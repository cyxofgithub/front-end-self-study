## 为什么两者要共同存在

- **VDOM**：对 UI 的抽象描述（What to render）。它是平台无关的纯 JS 对象树，只描述"界面长什么样"。
- **Fiber**：协调器（How to render / When to render）。负责调度 VDOM 的变更如何、何时应用到宿主环境。

两者职责不同：VDOM 关注 UI 的描述，Fiber 关注渲染的调度和执行。即便协调器发生变化，VDOM 的描述仍然可以复用。

---

## 什么时候协调器会发生变化？

**协调器（Reconciler）不是一成不变的，它已经在历史上变过，将来还会变。**

### 1. 已经发生过的变化：Stack → Fiber

|          | React 15 Stack Reconciler | React 16+ Fiber Reconciler |
| -------- | ------------------------- | -------------------------- |
| 执行方式 | 同步递归，一气呵成        | 异步可中断，分片执行       |
| 优先级   | 无                        | 支持任务优先级调度         |
| 中断恢复 | 不可中断                  | 可中断、可恢复             |
| 核心问题 | 长任务阻塞主线程、掉帧    | 通过时间切片解决           |

触发这个变化的原因：**VDOM diff 本身的计算量可能很大**，原来的同步递归会导致长时间占用主线程，用户交互（点击、输入）得不到响应。协调器需要从"一口气做完"升级为"可打断、分优先级"。

### 2. 协调器还可能怎么变？

- **调度策略变化**：当前 Fiber 的优先级调度（lane 模型）本身就是持续迭代的，比如 Concurrent Mode 对调度策略做了大幅调整。VDOM 不需要感知这些变化。
- **不同渲染目标**：同一个 VDOM 树可以由不同的协调器渲染到不同平台——`react-dom`、`react-native`、`react-three-fiber`、`react-pdf`、`ink(终端)`。每个平台的协调器逻辑完全不同，但 VDOM 是同一套。
- **未来可能的架构升级**：如果有一天 Fiber 被更好的架构替代（比如 React 团队探索过的更激进的编译时方案），VDOM 的概念仍然可以保留，只需要替换协调器。

总结：fiber 用于协调逻辑(可能会变) vdom是ui的抽象描述(上层逻辑变也不需要改变)而且不同平台还可以复用
