## 一、基础概念类（必问）

### 1. 什么是 WebRTC？它的核心目标是什么？

WebRTC（Web Real-Time Communication）是浏览器原生支持的实时通信 API 集合，无需安装插件/第三方应用，就能在浏览器间实现点对点（P2P）的音视频、数据传输。  
核心目标：让 Web 应用摆脱对第三方组件的依赖，实现低延迟、原生的实时音视频通话、数据共享。

### 2. WebRTC 的核心 API 有哪些？各自的作用是什么？

答案：  
| API | 核心作用 |
|-----|----------|
| `getUserMedia()` | 入口 API，获取本地音视频设备（麦克风/摄像头）的流（MediaStream） |
| `RTCPeerConnection` | 核心核心，管理 P2P 连接，处理音视频的编码、传输、解码 |
| `RTCDataChannel` | 基于 PeerConnection 的点对点数据通道，传输文本/二进制数据（如聊天、文件） |
| `RTCSessionDescription` | 封装 SDP 信息，用于两端协商音视频编码、网络等参数 |
| `RTCIceCandidate` | 封装 ICE 候选地址，解决 NAT 穿透，找到两端可达的网络路径 |

### 3. 什么是 SDP、ICE、STUN、TURN？核心关系是什么？

答案：

-   SDP（会话描述协议）：不是传输协议，是**文本格式**，描述音视频会话的编码、网络、媒体类型等参数，两端通过交换 SDP（Offer/Answer）协商通信规则；
-   ICE（连接建立框架）：解决 NAT 穿透，找到两端最佳通信路径；
-   STUN（NAT 遍历工具）：公网服务器，帮助终端获取自己的公网 IP+端口，优先实现直连；
-   TURN（中继遍历）：STUN 的补充，直连失败时作为中继转发数据（会增加延迟）；
    核心关系：ICE 框架依赖 STUN/TURN 服务器，优先 STUN 直连，失败则用 TURN 中继。

## 二、核心流程类（高频）

### 1. 简述 WebRTC 建立点对点音视频通话的完整流程？

答案：（需信令服务器辅助，WebRTC 本身不含信令）

1. 初始化：两端创建`RTCPeerConnection`实例，配置 STUN/TURN 服务器；
2. 获取本地流：调用`getUserMedia()`获取音视频流，添加到 PeerConnection；
3. 交换 SDP：发起方创建 Offer（SDP）→ 信令发给接收方 → 接收方创建 Answer（SDP）→ 信令返回发起方；
4. 交换 ICE 候选：两端触发`icecandidate`事件，通过信令互发候选，调用`addIceCandidate()`添加；
5. 建立连接：ICE 候选交换完成后，接收方触发`track`事件，获取远端流并渲染。

### 2. 为什么 WebRTC 需要信令服务器？WebRTC 自带信令吗？

-   必要性：WebRTC 需要交换 SDP（Offer/Answer）和 ICE 候选，还需处理通话邀请、挂断、房间管理等业务逻辑，这些都需要信令服务器中转；
-   核心结论：WebRTC**不包含**信令机制，需开发者基于 WebSocket/Socket.IO 自行实现。

## 三、实战应用类（重点）

### 1. 如何实现 WebRTC 屏幕共享？

答案：核心是用`getDisplayMedia()`替代`getUserMedia()`（浏览器原生支持）：

```javascript
async function getScreenStream() {
    try {
        // 获取屏幕流（支持选择窗口/屏幕，部分浏览器支持共享系统音频）
        const stream = await navigator.mediaDevices.getDisplayMedia({
            video: true,
            audio: false, // 可选：开启系统音频（Chrome/Firefox支持）
        });
        return stream;
    } catch (err) {
        console.error('获取屏幕流失败：', err);
        return null;
    }
}
```

注意：需 HTTPS 环境（localhost 除外），切换共享内容时需监听流变化。

### 2. 如何实现静音/关闭摄像头？

答案：直接操作 MediaStream 的 Track 状态：

```javascript
// 静音麦克风
function muteAudio(stream) {
    stream.getAudioTracks()[0].enabled = false;
}
// 关闭摄像头
function stopVideo(stream) {
    stream.getVideoTracks()[0].enabled = false;
}
// 恢复
function unmute(stream, type) {
    stream[`get${type}Tracks`]()[0].enabled = true;
}
```

### 3. 通话卡顿/延迟高的常见原因？

答案：

-   网络：带宽不足、丢包/抖动、NAT 穿透失败（走 TURN 中继）；
-   媒体：编码码率过高、设备性能不足（老旧设备编码压力大）；
-   代码：未配置 STUN/TURN、频繁创建销毁 PeerConnection、未处理 ICE 候选；
-   浏览器：兼容性问题、进程占用过高。

## 四、优化与问题排查类

### 1. 如何优化 WebRTC 通话质量？

答案：

1. 网络优化：配置可靠的 STUN/TURN，动态调整码率（通过`RTCRtpSender`）；
2. 媒体优化：优先用 VP8 编码（兼容性好），网络差时降低分辨率/帧率（如 720p→480p）；
3. 代码优化：复用 PeerConnection 实例，监听`iceconnectionstatechange`及时重连；
4. 设备优化：检测设备性能，低性能设备降低编码压力。

### 2. WebRTC 兼容性如何处理？

答案：

-   前置检测：`if (navigator.mediaDevices?.getUserMedia)`；
-   API 兼容：用 polyfill 处理旧版浏览器的前缀（如`webkitGetUserMedia`）；
-   编码兼容：优先 VP8，避免 AV1 等小众编码；
-   测试覆盖：主流浏览器（Chrome/Firefox/Edge）+ 移动端（iOS Safari 11+/Android Chrome）。

## 五、进阶扩展类

### 1. RTCDataChannel 和 WebSocket 的区别？

答案：  
| 维度 | RTCDataChannel | WebSocket |
|-----|----------------|-----------|
| 架构 | P2P（直连无需服务器） | C/S（所有数据经服务器转发） |
| 延迟 | 直连时极低 | 依赖服务器性能，延迟较高 |
| 依赖 | 需信令服务器建立连接 | 直接连接服务器即可 |
| 适用场景 | 点对点数据传输（如游戏同步、文件传输） | 客户端-服务器实时通信（如聊天、推送） |

### 2. 如何实现多人通话？

答案：主流两种方案：

1. Mesh（全网格）：每个用户与其他用户建立独立 PeerConnection，优点简单，缺点仅适合 3-4 人（连接数 N\*(N-1)/2）；
2. SFU（选择性转发单元）：基于媒体服务器（mediasoup/Janus），所有用户流发至服务器，服务器仅转发需要的流，适合 10+人通话（主流方案）。

---

### 总结

1. WebRTC 核心是 P2P 实时通信，依赖`RTCPeerConnection`、SDP 协商和 ICE（STUN/TURN）做 NAT 穿透，且必须搭配信令服务器；
2. 建立通话的核心流程是“创建 PeerConnection→ 获取本地流 → 交换 Offer/Answer→ 交换 ICE 候选 → 渲染远端流”；
3. 优化通话质量的关键是：配置可靠的 STUN/TURN、动态调整音视频参数、优先使用高效编码格式（如 VP8）。
