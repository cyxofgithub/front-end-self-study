# 多路视频并发解码，前端性能瓶颈怎么优化

> **一句话结论：** 瓶颈不在「拉流」而在「解码」——每路都是 H.264 压缩码流，必须先解码成帧才能渲染；GPU 硬解会话数有限，超出自动回落 CPU 软解，4 路 1080p 软解就打满一颗核心拖死整页。前端能做**两个维度**的事：**数量维度减路数**（限流/可见性/隐藏）和**质量维度降单路成本**（子码流降分辨率、降帧率、选硬解友好的编码）——不是只有可见性一招。

---

## 一、先定位：卡在哪（硬解 vs 软解）

解码开销的构成是理解所有优化手段的钥匙：

```
解码开销 ≈ 路数 × 单路解码开销
单路开销 ≈ 分辨率(像素数) × 帧率 × 编码复杂度 × (硬解? 软解)
```

网络传来的是压缩码流，不是像素。谁把码流解码成帧，决定了 CPU 会不会被拖死：

| | 硬解 | 软解 |
| --- | --- | --- |
| 执行者 | GPU 专用解码电路（NVDEC / Apple 媒体引擎） | CPU 通用指令 |
| 并发上限 | **会话数受显卡规格限制**，1080p 通常个位数~十几路 | 无会话概念，但每路吃 20%~50% 一个核心 |
| 超限后果 | 多出的路**自动回落软解** | CPU 打满 → 主线程排队 → 整页卡死 |

```mermaid
flowchart LR
    A[收到的 H.264 码流] --> Q{谁来解码}
    Q -- "前 N 路<br/>解码电路有空位" --> H[硬解: 不占 CPU]
    Q -- "第 N+1 路起<br/>会话数耗尽" --> S[软解: 吃 CPU]
    H --> R[像素帧 → video 渲染]
    S --> R
    S -. "CPU 满 → JS/渲染排队" .-> K[地图、表格全卡]
```

**直觉数字**：单路 1080p 软解吃 20%~50% 一个核心，4 路并发足以打满一颗。解码线程、主线程、合成线程共享同一个 CPU 池——所以卡的不只是视频，是**整页**。多路解码压力按「路数 × 分辨率 × 帧率」线性叠加，硬解那个隐形天花板一越过就是断崖式恶化。

## 二、前端能做的：两个维度（不是只有可见性）

### 数量维度：减少同时解码的路数

| 手段 | 做法 |
| --- | --- |
| **限制并发** | 宫格预算，超出显示封面/占位 |
| **可见性优先** | IntersectionObserver，视口外**关 PC**（不是 `video.pause()`） |
| **页面隐藏** | `visibilityState` 变 hidden 时全关（切后台不再白耗解码） |

> `video.pause()` 省不了多少——**解码仍在浏览器里进行**。关 `RTCPeerConnection` 才真正释放解码会话与带宽。

### 质量维度：降低每一路的解码成本（同样重要）

| 手段 | 做法 | 收益 |
| --- | --- | --- |
| **拉子码流** | 多画面墙拉 480p 子流（看态势不看细节） | 像素数 1/4 → 解码开销 1/4 起 |
| **降帧率** | 监控 15fps 足够，让服务端发低帧率档 | 解码开销随帧率线性下降 |
| **选编码** | 优先 H.264（硬解支持最广），避开只软解的 H.265/AV1 | 决定「硬解还是软解」这一刀 |

**编码选择是最容易被忽略的一刀**：硬解/软解不是前端「切」出来的，而是**编码格式 × 机器能力**共同决定的——

- H.264：几乎所有 GPU/SoC 都带硬解，是监控拉流首选；
- H.265：带宽省一半，但硬解覆盖不如 H.264 广，软解 H.265 比 H.264 更吃 CPU；
- VP9/AV1：硬解只有新硬件支持，AV1 软解极贵。

前端控制手段：SDP 里 codec 顺序、`RTCRtpReceiver.setCodecPreferences`、或信令告诉 SFU 只发 H.264。

## 三、前端真正的做法：流预算管理器

浏览器没有「硬解/软解切换」的 API（WebCodecs 的 `VideoDecoder` 能指定 `hardwareAcceleration` 偏好，但 WebRTC 拉流要自己解封装 RTP，工程复杂一般不这么干）。前端落地 = 一个管理器同时管两个维度：

```typescript
class VideoWall {
  private slots = new Map<string, StreamSlot>();
  private observer: IntersectionObserver;

  constructor(private container: HTMLElement, private maxActive = 9) {
    this.observer = new IntersectionObserver(this.onIntersect, {
      root: this.container,
      rootMargin: '120px', // 提前预拉，滚动不闪黑
    });
  }

  private onIntersect = (entries: IntersectionObserverEntry[]) => {
    for (const entry of entries) {
      const id = (entry.target as HTMLElement).dataset.streamId!;
      this.slots.get(id)!.visible = entry.isIntersecting;
    }
    this.sync();
  };

  private sync() {
    const candidates = [...this.slots.values()]
      .filter((s) => s.visible || s.pinned)                    // 数量维度：可见或置顶才进预算
      .sort((a, b) => this.score(b) - this.score(a));
    const activeIds = new Set(candidates.slice(0, this.maxActive).map((s) => s.id));

    for (const slot of this.slots.values()) {
      if (activeIds.has(slot.id)) this.start(slot);             // 预算内 → 拉流
      else this.stop(slot);                                     // 预算外 → 关 PC
    }
  }

  private score(s: StreamSlot) {
    return (s.pinned ? 1000 : 0) + (s.visible ? 100 : 0) + (s.priority ?? 0);
  }

  private start(slot: StreamSlot) {
    if (slot.player) return;
    // 质量维度：置顶/告警路拉主码流，其余拉子码流
    const url = slot.pinned ? slot.mainUrl : slot.subUrl ?? slot.mainUrl;
    slot.player = new StreamPlayer(slot.el, url);
    slot.player.start();
  }

  private stop(slot: StreamSlot) {
    slot.player?.destroy();      // 关 PC 才真正释放解码会话与带宽
    slot.player = null;
    slot.el.srcObject = null;
  }
}
```

**策略**：数量维度——视口外直接 `destroy()`、超预算只留封面；质量维度——置顶/告警路保主码流，其余可见路优先子码流。

## 面试回答

> 多路视频的瓶颈是解码不是拉流：每路 H.264 都要解码成帧，GPU 硬解会话数有限，超出的路回落软解，4 路 1080p 软解就打满一颗核。前端没有硬解软解切换 API，但有两个维度的优化。数量维度减路数：限制并发、视口外关 PC 而不是 pause（pause 省不了解码）、页面隐藏时全关。质量维度降单路成本：多画面墙拉子码流，像素降到 1/4、解码开销降到 1/4；降帧率，监控 15fps 足够；选编码，优先 H.264 因为硬解最广，避开软解更贵的 H.265/AV1。核心是一个流预算管理器，按「可见性 + 置顶 + 优先级」评分，只让预算内的路解码、非重点路拉子码流。
