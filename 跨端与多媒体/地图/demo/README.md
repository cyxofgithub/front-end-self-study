## 怎么看效果

1. 默认参数（120 车 × 8Hz ≈ 960 条消息/秒）：左（策略 A）重绘次数/秒 ≈ 消息数/秒，单次重绘耗时开始上涨；右（策略 B）稳定 60 帧重绘/秒，且「同帧合并消息」持续计数——这就是「消息频率与渲染频率解耦」。
2. 把车辆数拉到 300+、频率拉到 15Hz+：左面板单次重绘耗时与页面帧率一起崩（主线程被打满），右侧仍稳定——这是面试里「高频数据更新优化」的实证。
3. 频率拉到 1~2Hz：左面板车辆在两次消息之间完全静止、逐格跳变；右侧靠插值平滑持续移动——「上报低频、渲染高频」的补帧价值。
4. 勾掉「B：视野裁剪」对比绘制车辆数：视口外的车（压暗区域）被裁剪后完全不参与绘制。

## 真实 / 模拟边界

| 部分 | 状态 | 生产中对应 |
| --- | --- | --- |
| 底图（网格 + 道路） | Canvas 模拟 | 高德/百度底图（SDK 内部 WebGL 渲染） |
| 车辆标记 | Canvas 三角形 | `AMap.Marker`（DOM）或 `CustomLayer` 自绘 |
| 消息源 | `setInterval` 本地生成，每车固定 Hz + 抖动 | MQTT 订阅回调（车端 1~10Hz 上报） |
| 策略 A/B 消费逻辑 | **真实代码，即文档结论** | `pending` 缓冲 + rAF 每帧消费 + 指数平滑 + `getBounds().contains()` 裁剪 |

> 策略 B 的 `tickB()` / `onMessageB()` 与 [../高德地图与高频轨迹渲染.md §3.1](../高德地图与高频轨迹渲染.md) 的 `VehicleLayer` 是同一套思路的 canvas 版：`pending` Map = 最新值缓冲，`0.2` 系数 lerp = 指数平滑，`continue` = 视野裁剪。

## 为什么用 Canvas 模拟而不是真接高德 SDK

真实高德需要 key + 安全密钥，且 DOM Marker 的每次 `setPosition` 成本无法稳定计量。本 demo 用「每条消息一次整幅 Canvas 重绘」等价模拟「每条消息一次 DOM 样式更新」的主线程占用模型——结论（合帧/裁剪/插值的收益）对 DOM Marker、Canvas、WebGL 三层渲染同样成立，见 [../地图SDK选型与WebGL可视化.md §6](../地图SDK选型与WebGL可视化.md)。
