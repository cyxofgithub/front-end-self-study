# 小程序性能监测与优化

## 一句话结论

小程序性能要拆成启动、逻辑层、通信桥、渲染层和内存五类指标观察；先定位哪一层超时，再决定是减少计算、减少跨层更新、减少节点，还是释放资源。

配套实验：[小程序性能监测 Demo](./demo/小程序性能监测-demo/README.md)
项目目录：[小程序性能监测-demo](./demo/小程序性能监测-demo/)

## 完整链路

    启动与代码包 -> 逻辑层 JS -> setData / 事件通信 -> 渲染层布局绘制 -> 屏幕帧
                         |                         |
                         +------ 网络请求 ----------+------ JS 状态、缓存、临时对象

不要只看 FPS。FPS 正常但内存持续增长，仍然可能最终崩溃；FPS 下降也不一定是逻辑层慢，可能是通信数据太大或渲染节点太多。

## 监测指标

| 维度 | 指标 | 用来判断 |
| --- | --- | --- |
| 启动 | 冷启动、热启动、首屏可操作 | 代码包、初始化和首屏请求是否阻塞 |
| 逻辑层 | JS 长任务、事件延迟、请求耗时 | 业务计算和回调是否过重 |
| 通信桥 | setData 次数、单次 payload、累计数据量 | 是否频繁传输或重复传输大对象 |
| 渲染层 | FPS、掉帧、节点数、布局绘制耗时 | 组件树和视图更新是否过重 |
| 内存 | JS 状态、图片、Canvas、缓存、增长趋势 | 是否存在泄漏或资源未释放 |

## 微信小程序如何监测

### 开发者工具和真机

用微信开发者工具录制完整操作，再在低端真机复测：

    打开页面 -> 开始录制 -> 滚动 / 输入 / 动画 / 流式输出 -> 停止录制

重点把卡顿时刻和业务动作对应起来：

| 现象 | 优先检查 |
| --- | --- |
| 点击后很久没有反馈 | 同步初始化、逻辑层长任务、请求等待 |
| 输入时卡顿 | 高频事件、每次输入都 setData、列表整页更新 |
| 滚动掉帧 | 节点数量、图片解码、复杂富文本 |
| 流式输出越久越卡 | 完整消息列表重复传输、节点持续增长 |
| 返回页面后内存不降 | 定时器、监听器、请求、图片和缓存 |

真机至少验证：

    冷启动 -> 首屏可操作
    连续滚动 30 秒 -> FPS 与内存趋势
    接收长消息 -> 输入是否仍然响应
    切后台 30 秒再回来 -> 请求和定时器是否正确恢复
    反复进入退出 20 次 -> 内存是否持续上升

### 业务埋点

工具适合排查，埋点适合发现线上回归。每次采样至少带上版本、机型、系统、基础库版本和页面路径。

    const start = Date.now();
    wx.request({
      url: '/api/chat',
      success() {
        reportMetric('chat_request_duration', Date.now() - start);
      },
      fail(error) {
        reportMetric('chat_request_error', 1, { code: error.errMsg });
      },
    });

reportMetric 应统一封装采样率、脱敏、批量上报和失败降级。

### Performance 能力

部分基础库提供性能相关 Performance 能力，但条目和可用接口会随平台、基础库和运行环境变化。使用前要做能力检测，并在真机确认数据含义。

    const performanceApi = typeof wx.getPerformance === 'function'
      ? wx.getPerformance()
      : null;

    if (performanceApi) {
      // 按目标基础库支持的接口观察启动、脚本、渲染或请求条目。
    }

它适合补充细粒度数据，不能替代开发者工具时间线和真机验证。

## 内存怎么监测

### 看趋势，不看单点

图片解码、Canvas、页面切换和 GC 都可能造成短时峰值。真正可疑的是重复同一流程后，内存长期回不到原来的稳定区间。

    周期采样内存 -> 重复进入 / 退出页面 -> 比较回收后的稳定区间
                                      |
                         不回落 -> 检查引用、监听器、定时器、请求、缓存

常见来源：

| 来源 | 典型问题 | 处理方式 |
| --- | --- | --- |
| 消息列表 | 历史消息无限增长 | 分页、裁剪、归档 |
| 图片 | 原图过大、缓存无上限 | 压缩、按需加载、限制缓存 |
| Canvas | 画布过大、重复创建 | 控制尺寸、复用、销毁时清理 |
| 定时器和监听器 | 页面退出后仍运行 | 注册与注销成对出现 |
| 请求回调 | 页面销毁后仍持有引用 | 取消请求或忽略过期回调 |

## 配套 Demo 怎么用

用微信开发者工具导入 [小程序性能监测-demo](./demo/小程序性能监测-demo/)，编译后点击开发者工具顶部工具栏的“性能”面板，再回到 Demo 页面开始实验。这个 Demo 是原生小程序页面，真正调用页面的 setData、wx.nextTick、页面生命周期和可用的 wx.getPerformance 能力。

1. 选择“逐事件更新”，设置 300 个节点、30 个事件/秒、4 KB payload，点击开始。
2. 记录页面内的 setData 更新次数、更新回调耗时、wx.nextTick 延迟和模拟通信量，同时观察开发者工具性能时间线。
3. 保持参数不变，切换为“批量更新”，比较两种策略的更新次数和页面响应。
4. 勾选“模拟未释放内存”，运行一段时间后停止并重置，观察 wx.getPerformance 可用时的 JS Heap 和性能面板内存趋势。

Demo 的对应关系：

| Demo 指标 | 模拟内容 | 限制 |
| --- | --- | --- |
| setData 更新 | 页面实际发生的逻辑层到渲染层更新 | 回调耗时仍受设备和基础库影响 |
| nextTick 延迟 | 当前视图更新后的调度延迟 | 不等于 FPS 或下一帧时间 |
| 模拟通信量 | payload 和节点数据的传输压力 | Demo 没有暴露底层桥接耗时 |
| JS Heap | 逻辑对象增长趋势 | 不能读取微信宿主和原生组件完整内存 |
| 开发者工具 FPS | 真实小程序运行时的帧率 | 应以真机结果为准 |

## 优化决策

    卡顿或内存上涨
      -> 启动问题：检查主包、同步初始化、首屏请求
      -> 输入/滚动问题：检查事件频率、setData 数据量、节点数量
      -> 流式问题：缓冲、批量更新、只传变化字段
      -> 内存问题：检查引用、监听器、定时器、请求和缓存

## 面试回答模板

> 我会先用开发者工具和真机把问题拆成启动、逻辑层、通信桥、渲染层和内存五类指标。FPS 下降时看 JS 长任务、setData 次数和 payload、节点数量以及图片和富文本；内存问题做重复进出页面的趋势测试，检查定时器、监听器、请求回调、消息列表、图片和 Canvas 是否释放。线上再按版本、机型和页面上报启动耗时、请求耗时、错误率和关键交互耗时。
