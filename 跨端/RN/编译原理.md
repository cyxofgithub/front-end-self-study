### React Native 运行原理（核心不是传统“编译”）

首先要明确：RN 并非像原生应用（iOS/Android）那样把代码直接编译成机器码，而是一种**混合运行**的模式，核心是“JS 逻辑 + 原生渲染”，其核心原理可以拆解为以下几个关键环节：

#### 1. 核心架构：JS 线程 + 原生线程分离

RN 应用运行时会启动两个核心线程：

-   **JS 线程**：执行你的 JS/TS 代码（包括组件逻辑、状态管理、业务逻辑），运行在 JS 引擎中（iOS 是 JSC/JavaScriptCore，Android 常见 Hermes 引擎，比 JSC 更轻量、启动更快）。
-   **原生线程**：用原生语言实现，iOS 端是 Objective-C/Swift，Android 端是 Java/Kotlin。主要负责 UI 渲染、原生组件（如 View、Text、Button）的创建，以及系统能力调用（如相机、网络等），这些都是由各自平台的原生系统（iOS/Android）接管。

#### 2. 执行流程（从代码到界面）

可以把整个过程理解为“JS 发指令，原生做执行”，具体步骤：

1. **代码预处理**

    - 你写的 `.js/.ts/.jsx/.tsx` 代码，首先会通过 Metro（RN 官方打包工具）进行**打包**（不是编译）：将多个 JS 文件合并成一个或多个 bundle 文件（JS 代码包），同时处理 ES6+ 转 ES5、TS 转 JS、图片/资源路径映射等。
    - 这个阶段只做“代码整合和语法转换”，不生成原生代码。

2. **JS 引擎执行逻辑**

    - 应用启动后，原生端会启动 JS 引擎（如 Hermes），加载并执行打包后的 JS bundle。
    - JS 代码执行过程中，会通过 RN 提供的 `React Native Bridge`（桥接层），将“UI 渲染指令”“原生能力调用请求”（如 `Alert.alert()`）转换成**序列化数据**（JSON 格式），发送给原生线程。

3. **桥接层（Bridge）：JS 与原生的通信桥梁**

    - Bridge 是 RN 的核心，本质是一个**异步通信通道**（基于 TCP 或原生消息队列），负责 JS 线程和原生线程之间的数据传递：
        - JS 向原生发请求（如“创建一个红色的 View，宽 100，高 50”）；
        - 原生执行完后，将结果（如“View 创建成功”“网络请求返回数据”）回传给 JS 线程。
    - 注意：Bridge 是异步的，这也是 RN 中部分操作（如原生模块调用）不能同步执行的原因。

4. **原生端渲染 UI**
    - 原生线程接收到 JS 发来的渲染指令后，会调用对应的原生组件（iOS 是 UIKit，Android 是 Android SDK）创建真实的原生控件；
    - 这些原生控件最终渲染在屏幕上，用户看到的界面本质上是原生 UI，而非 WebView 渲染的 H5 界面（这是 RN 和 Cordova/PhoneGap 的核心区别）。

#### 3. 补充：新架构（Fabric + TurboModules）

为了解决传统 Bridge 异步通信的性能瓶颈（如 UI 更新延迟），RN 推出了新架构：

-   **Fabric**：重构了 UI 渲染层，让 JS 可以直接访问原生组件的“句柄”，无需通过 Bridge 序列化传递，实现 UI 渲染的同步化；
-   **TurboModules**：优化了原生模块调用，支持懒加载、同步调用，提升原生能力的调用效率。

### 总结

RN 的核心运行逻辑可以总结为 3 个关键点：

1. **非纯编译**：RN 不将 JS 编译为原生代码，而是通过 Metro 打包 JS 代码，在 JS 引擎中执行；
2. **桥接通信**：JS 线程通过 Bridge 向原生线程发送指令，原生线程负责实际的 UI 渲染和系统能力调用；
3. **原生渲染**：最终界面是原生控件渲染的，而非 Web 界面，这保证了 RN 应用的原生体验。
