## 在过去遇到的最大的技术挑战

近期就是我在做这个数据服务平台数据处理模块的时候，它本质其实就一个 sql 的可视化操作页面

难点主要有几个方面：

-   一个是业务的理解成本，我需要去梳理清除这些节点背后映射的是那些 sql 语句，因为只有梳理清楚这些东西你才能知道要怎么去设计每个节点的数据结构既要方便去映射到后台的 sql 语句又要方便我这边对节点位置、连线等基础状态的获取；其实这些 sql 节点都可以抽象成一个流程节点，首先要去确定好节点模型基础的属性，比如节点的位置、前后节点 id 等等，然后后台 sql 这些比较业务的描述我是统一放在一个属性里，然后后台去定义清楚，然后再一起对齐一下看看有没有问题需不需要去做调整

-   一个是技术实现的难度，首先它是可视化的流程图，它的交互相对比较复杂需要做拖拽、连线、选中等操作，那我就需要提前去调研怎么去实现它，当时我是去找一些相同场景的应用，比如像 dify、coze 了解清除他们是用什么样的技术去实现这个功能的，然后尝试去做一个 demo，看看能否满足产品需求（像 dify 用的就是 react flow，这个库其实也是现在 react 生态里实现流程图比较主流的一个库，最主要的是它能满足我们的需求，比如节点样式的自定义，然后再性能方面也支持节点的懒加载、虚拟滚动）。

-   一个是它整个模块状态也比较多，处理对流程节点的管理还需要管理任务状态、任务的运行设置、编辑的历史记录等等。当时我是划分了两个数据模型，一个是任务的模型，一个是节点模型，任务模型去处理这些全局操作，节点模型就是针对流程图的管理

-   还有就是联调成本，不同的 sql 节点拼装后数据是否正确、起码我自侧的时候要覆盖每个节点的场景去做自侧，但是这样就很麻烦，我当时是用 ai 帮我写一个节点对象转 sql 的脚本，然后我直接拿 sql 查后台的表再去做核对

-   一个是时间也比较急，我们在赶一个展会演示，mvp 思维，写好 todo

## 低代码相关

### 低代码引擎为什么要自己设计

-   阿里的 lowcode-engine 的定位是页面级的编排，所以框架会比较重，比如里面包含了对交互事件的处理、数据源的处理，定位的用户偏向有技术背景的人员，而且它对编辑器的自定义也比较有限；百度的 amis 定位更倾向于 json 配置代码，所以对编辑器的支持也比较少；而我们的场景更多是提供一些现成的组件给用户做简易的编排和属性的修改，更轻量级
-   性能问题：编辑端和渲染端耦合，编辑端需要拖拽、配置面板、选中的能力，渲染端其实只需要渲染能力
-   维护问题：这些低代码框架其实挺重的，如果真出了问题能不能及时修复，如果要自己去啃源码成本也很高

### 低代码渲染性能问题怎么优化

其实思路跟我们平时优化页面也差不多：

-   组件层面的优化：

    -   尽可能减少重排重绘
    -   减少节点数量、用缓存、防抖、批量更新限制不必要的重渲染

-   引擎层面的优化：
    -   目前我们还没有做比较系统性的性能，但是我们在设计的时候也会尽可能去避免掉一些性能问题，比如组件加载策略，我们是支持全量加载/按需加载，渲染端和编辑端的拆分，拓展层插件的按需引用。
    -   虽然我们做了一部分但是我为什么说没有系统性的优化，因为其实低代码渲染的主要性能问题在于渲染过程中 shema 的动态解析这会造成一定时间的白屏，但是我也有思路，如果我们是静态页面，可以把目前的 dom 节点做个快照。我们记录这份快照，还有通过 document.styleSheets 导出完整的样式表，下次渲染的时候就可以绕开引擎直接渲染
    -   如果是动态页面，会比较麻烦但也有可行性，将组件编译为渲染函数，下次引擎直接调用渲染函数进行渲染，避免 schema 解析时间

### 负责的低代码模块核心架构是什么？

我负责了组件库、编辑器部分模块的设计，具体涉及到到内容就是属属性面板插件、属性设置器等扩展能力，说得简单点就是如何把抽象定义和相关配置转换成真实渲染的面板和对应的属性设置器，怎么去减少重复的工作和开发效率以及一些定制化的需求
