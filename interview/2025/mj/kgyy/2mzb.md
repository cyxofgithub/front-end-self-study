## 在过去遇到的最大的技术挑战

近期就是我在做这个数据服务平台数据处理模块的时候，它本质其实就一个 sql 的可视化操作页面

难点主要有几个方面：

-   一个是业务的理解成本，我需要去梳理清除这些节点背后映射的是那些 sql 语句，因为只有梳理清楚这些东西你才能知道要怎么去设计每个节点的数据结构既要方便去映射到后台的 sql 语句又要方便我这边对节点位置、连线等基础状态的获取，那我们怎么去解决这个问题，其实对前端而言所有的这些节点都可以抽象成一个流程节点，我只需要定义好这个节点模型基础的属性，然后后台 sql 这些比较业务的描述我是统一放在一个属性里，然后后台去定义清楚，然后再一起对齐一下看看有没有问题需不需要去做调整

-   一个是技术实现的难度，首先它是可视化的流程图，它的交互相对比较复杂需要做拖拽、连线、选中等操作，那我就需要提前去调研怎么去实现它，那我是怎么做这个事情的，首先我是去找一些相同场景的应用，比如像 dify、coze 了解清除他们是用什么样的技术去实现这个功能的，像 dify 用的就是 react flow，这个库其实也是现在 react 生态里实现流程图比较主流的一个库，最主要的是它能满足我们的需求，比如节点样式的自定义，然后再性能方面也支持节点的懒加载、虚拟滚动。

-   一个是它整个模块状态也比较多，处理对流程节点的管理还需要管理任务状态、任务的运行设置、编辑的历史记录等等。当时我是划分了两个数据模型，一个是任务的模型，一个是节点模型，任务模型去处理这些全局操作，节点模型就是针对流程图的管理

-   还有就是联调成本，不同的 sql 节点拼装后数据是否正确、起码我自侧的时候要覆盖每个节点的场景去做自侧，但是这样就很麻烦，我当时是用 ai 帮我写一个节点对象转 sql 的脚本，然后我直接拿 sql 查后台的表再去做核对

-   一个是时间也比较急，我们在赶一个展会演示，mvp 思维，写好 todo
