## 三者区别

| 对比维度               | HLS/FLV 拉流（HTTP 协议）                                   | WebRTC 拉流（P2P/中继协议）                                                      |
| ---------------------- | ----------------------------------------------------------- | -------------------------------------------------------------------------------- |
| **连接类型**           | 短连接（HTTP），一次请求一次响应，无状态                    | 长连接（P2P/中继），全程维持，有状态                                             |
| **服务器角色**         | 静态资源分发者（仅返回预设资源，无需协调）                  | 信令协调者+数据中转者（全程参与，复杂互动）                                      |
| **核心延迟**           | HLS：10-30 秒；FLV：1-5 秒（天生高延迟，源于分片/流式缓存） | 几十~几百毫秒（天生低延迟，源于实时数据包传输）                                  |
| **兼容性**             | 极强（全平台覆盖，Safari 原生支持，无需复杂适配）           | 中等（仅现代浏览器支持，IE 不兼容，移动端适配复杂）                              |
| **服务成本/压力**      | 极低（支持 CDN 缓存，大规模分发时服务器压力几乎不变）       | 极高（每个观众都需要独立长连接+可能的中继中转，高并发时服务器带宽/内存瓶颈明显） |
| **开发/维护复杂度**    | 低（依赖 hls.js/flv.js，几行代码实现，异常处理简单）        | 高（需处理信令协商、ICE 候选、断线重连、跨网中转等，兼容问题多）                 |
| **资源消耗（观众端）** | 低（仅解析视频流，无需维护复杂连接状态）                    | 高（需维护 P2P 连接、处理实时数据包，占用更多 CPU/内存）                         |
| **大规模分发友好性**   | 极佳（CDN 天然适配，支持万级/十万级观众）                   | 极差（P2P/中继难以支撑高并发，CDN 无法直接缓存）                                 |
| **核心适用场景**       | 普通观众单向观看，大规模分发，兼容优先                      | 双向互动场景（如连麦），低延迟优先，小规模观众                                   |

### hls 高延迟原因

把流切换成分片需要时间，对比 flv、webrtc 这种流式转发传输会延迟性高

### FLV 比 HLS 更快的核心原因

1. 封装格式：FLV 是二进制封装，索引内嵌，解析快；HLS 是文本 + 二进制封装，索引独立，解析慢。
2. 传输协议：FLV 基于 RTMP 实时协议，传输效率高；HLS 基于 HTTP，传输效率低。
3. 播放逻辑：FLV 是边下载边播放，无缓冲；HLS 是下载完再播放，有缓冲。
4. 分片策略：FLV 分片连续无缝；HLS 分片独立可能有间隙。

### 为什么 HLS 现在更流行？

尽管 HLS 播放速度慢，但它有两个不可替代的优势：

-   跨平台兼容性：HLS 基于 HTTP，几乎所有设备（手机、电脑、电视、浏览器）都支持，无需安装额外的播放器。
-   容错性和适应性：HLS 支持 ABR（自适应码率） 和容错，适合直播和点播等复杂场景。
