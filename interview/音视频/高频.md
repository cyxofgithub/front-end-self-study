# 前端音视频高频面试题（含标准答案+踩分点）

## 一、HTML5 音视频基础核心（必考，入门必问）

### 面试题 1：HTML5 video/audio 标签的核心属性、事件、方法有哪些？

#### 核心考点

原生音视频 API 掌握程度，自定义播放器的底层基础，区分高频业务 API 与冷门 API。

#### 标准答案

##### 核心必答点

1.  **核心属性（自定义播放器必用）**
    | 分类 | 核心属性 | 作用 |
    |---|---|---|
    | 基础控制 | `src` | 音视频资源地址 |
    | | `autoplay` | 自动播放（受浏览器策略限制） |
    | | `muted` | 是否静音（自动播放唯一通用兜底方案） |
    | | `loop` | 是否循环播放 |
    | | `controls` | 是否显示浏览器原生控件 |
    | | `preload` | 预加载策略，可选`none`(不预加载)/`metadata`(仅预加载元数据)/`auto`(自动预加载) |
    | | `currentTime` | 当前播放进度（秒，可读写，实现进度条拖拽） |
    | | `duration` | 音视频总时长（秒，只读） |
    | | `paused` | 是否处于暂停状态（只读） |
    | | `volume` | 音量，取值 0-1（可读写） |
    | | `playbackRate` | 播放倍速，0.5-16（可读写，实现倍速播放） |
    | 兼容性关键 | `crossorigin` | 解决跨域问题，可选`anonymous`(不带凭据)/`use-credentials`(带 cookie) |
    | | `playsinline` | iOS Safari 内联播放，禁止自动弹出全屏 |
    | | `webkit-playsinline` | iOS 低版本兼容内联播放 |
    | | `x5-playsinline` | 微信 X5 内核兼容内联播放 |

2.  **核心事件（生命周期+业务核心）**

    -   元数据加载：`loadedmetadata`（元数据加载完成，可获取正确时长、宽高，解决 duration 为 NaN 的核心事件）
    -   可播放事件：`canplay`（加载了足够数据，可开始播放）、`canplaythrough`（预估可流畅播放完）
    -   播放状态：`play`（触发播放）、`playing`（真正开始播放）、`pause`（触发暂停）、`ended`（播放结束）
    -   进度更新：`timeupdate`（currentTime 变化触发，进度条更新核心事件）、`seeking`/`seeked`（拖拽进度中/完成）
    -   缓冲相关：`progress`（缓冲数据更新）、`waiting`（缓冲不足导致播放卡顿）、`canplay`（缓冲恢复）
    -   异常事件：`error`（播放/加载失败）、`stalled`（加载中断）

3.  **核心方法**
    -   `play()`：触发播放，返回 Promise，播放失败会 reject（自动播放场景必须捕获异常）
    -   `pause()`：触发暂停
    -   `load()`：重新加载媒体资源（切换 src、修改 src 后必须调用）
    -   `requestFullscreen()`：进入全屏（带浏览器前缀兼容）、`exitFullscreen()`：退出全屏

##### 进阶加分点

-   区分`play`和`playing`的差异：`play`是调用播放方法时触发，此时可能还在缓冲；`playing`是真正开始渲染画面时触发，是判断起播成功的核心事件。
-   业务坑点：`preload="auto"`在移动端会被浏览器忽略，无法强制预加载；`duration`对直播流返回`Infinity`。

### 面试题 2：浏览器音视频自动播放策略是什么？如何解决自动播放失败问题？

#### 核心考点

浏览器安全策略理解，业务高频坑的解决能力，区分合规方案与兜底方案。

#### 标准答案

##### 核心必答点

1.  **浏览器核心自动播放规则（Chrome/Safari 通用核心）**

    -   规则 1：**静音的音视频，所有浏览器均允许自动播放**（唯一全平台通用的合规方案）。
    -   规则 2：**非静音的音视频，必须满足「用户已与当前文档域有过有效交互」（点击、触摸、键盘输入等）**，浏览器才允许自动播放。
    -   规则 3：无用户交互的页面，非静音媒体自动播放 100%被拦截；高用户活跃度的站点，浏览器会动态白名单，放宽限制。
    -   补充：iOS Safari、微信内置浏览器规则更严格，即使静音，也需开启`playsinline`才能内联自动播放，禁止自动全屏。

2.  **标准解决方案（按优先级排序）**
    -   方案 1：**默认静音自动播放，引导用户手动开启声音**。页面加载后直接调用`video.muted=true`+`video.play()`，同时在播放器 UI 上显示「开启声音」按钮，用户点击后取消静音，符合所有浏览器规则。
    -   方案 2：**用户交互前置，提前获取播放权限**。在用户进入播放页面前的上一步（比如点击进入直播间、点击视频卡片），就触发一次空的播放/暂停操作，让浏览器记录用户交互，进入页面后即可非静音自动播放。
    -   方案 3：**播放异常兜底**。调用`play()`时必须用 Promise 捕获异常，若播放失败，立即降级为静音播放，同时弹出 UI 引导用户点击开启播放/声音。
        示例代码：
    ```javascript
    async function autoPlay() {
        try {
            await video.play();
            console.log('自动播放成功');
        } catch (err) {
            console.log('自动播放失败，降级静音播放');
            video.muted = true;
            await video.play();
            // 显示开启声音按钮
            showAudioButton();
        }
    }
    ```

##### 进阶加分点

-   避坑点：不要用定时器延迟播放，无用户交互的延迟播放依然会被拦截；不要用 iframe 嵌套绕过，Chrome 已封堵该漏洞。
-   进阶方案：使用 Media Session API，配合浏览器锁屏媒体控制，提升用户交互后的播放权限（在锁屏场景下控制播放时可用）。

### 面试题 3：video 标签的跨域问题如何解决？`crossorigin`的两个取值有什么区别？

#### 核心考点

媒体资源跨域规则，CORS 配置，前端跨域场景的处理能力。

#### 标准答案

##### 核心必答点

1.  **video 跨域问题的触发场景与根因**

    -   根因：浏览器的同源策略，当 video 标签的媒体资源地址与当前页面域名不同源（协议、域名、端口任一不一致）时，会触发跨域限制。
    -   典型触发场景：
        1.  用 canvas 对 video 视频进行截图、生成封面时，会报「画布被跨域资源污染」，无法调用`toDataURL()`/`getImageData()`。
        2.  带鉴权 cookie 的跨域媒体资源，无法正常加载。
        3.  MSE 播放跨域流媒体时，资源加载失败。

2.  **标准解决方案**

    -   第一步：给 video 标签添加`crossorigin`属性，声明跨域访问模式。
    -   第二步：媒体资源的服务端配置 CORS 跨域响应头，返回`Access-Control-Allow-Origin`，允许前端页面域名访问；若带凭据，需额外返回`Access-Control-Allow-Credentials: true`。

3.  **`crossorigin`两个取值的核心区别**
    | 取值 | 核心行为 | 适用场景 | 服务端要求 |
    |---|---|---|---|
    | `anonymous`（默认） | 跨域请求**不携带 cookie、HTTP 认证等凭据** | 绝大多数公开的、无鉴权的跨域媒体资源 | 只需返回`Access-Control-Allow-Origin`，可设为`*`或页面域名 |
    | `use-credentials` | 跨域请求**携带 cookie 等凭据** | 需用户鉴权的私有媒体资源（比如付费视频） | 1. 必须返回`Access-Control-Allow-Origin: 具体页面域名`，不能为`*`；2. 必须返回`Access-Control-Allow-Credentials: true` |

##### 进阶加分点

-   避坑点：`crossorigin`属性必须在媒体资源`src`赋值之前设置，否则会导致设置失效；若资源已加载，需调用`load()`重新加载才能生效。
-   特殊场景：HLS 的 m3u8 索引文件和 TS 分片，若跨域，不仅 video 要加`crossorigin`，hls.js 的 AJAX 请求也需配置`withCredentials`对应`crossorigin`的取值。

## 二、流媒体协议与播放原理（必考，中高级核心）

### 面试题 1：常见流媒体协议有哪些？HLS/HTTP-FLV/RTMP/WebRTC/DASH 的特点、适用场景、浏览器兼容性对比？

#### 核心考点

流媒体体系认知，直播/点播的协议选型能力，区分各协议的核心差异。

#### 标准答案

##### 核心必答点

先给核心结论：**前端浏览器场景，点播首选 HLS，国内直播首选 HTTP-FLV，超低延迟实时互动首选 WebRTC**。

各协议核心对比表（面试必答核心）：
| 协议 | 核心原理 | 典型延迟 | 浏览器原生兼容性 | 核心优点 | 核心缺点 | 适用场景 |
|---|---|---|---|---|---|---|
| HLS | 苹果推出，基于 HTTP，把媒体切成 TS 分片，通过 m3u8 索引文件管理分片 | 标准 HLS 3-10s，LL-HLS 1-3s | 全平台原生支持（iOS Safari 全系、安卓 Chrome、微信等） | 兼容性拉满，CDN 友好，天然支持 ABR 自适应码率，穿墙能力强 | 标准版本延迟高，不适合超低延迟直播 | 点播、泛娱乐直播、跨境直播、全平台兼容的播放场景 |
| HTTP-FLV | 把 RTMP 协议封装在 HTTP 中，流式传输 FLV 格式媒体数据 | 1-3s | 无原生支持，需依赖 flv.js+MSE 实现 | 延迟低，实现简单，国内 CDN 广泛支持，内存占用低于 HLS | iOS Safari 原生不支持，需额外兼容 | 国内直播、电商直播、游戏直播，对延迟有要求的非互动直播 |
| RTMP | 基于 TCP 的 Adobe 实时消息协议，长连接流式传输 | 1-3s | 浏览器完全不支持，需 Flash/插件 | 延迟低，是国内直播 CDN 的标准上行协议 | 浏览器无原生支持，TCP 弱网下卡顿明显，端口易被防火墙拦截 | 主播推流上行，不用于浏览器播放端 |
| WebRTC | 谷歌推出的网页实时通信标准，基于 UDP/SRTP，P2P/媒体服务器传输 | 100-500ms | 现代浏览器全支持（Chrome/Firefox/Safari11+） | 超低延迟，支持 P2P，内置回声消除、降噪等音视频处理，弱网抗性强 | 实现复杂度高，CDN 支持度低，带宽成本高 | 1v1 视频通话、多人连麦、直播互动、在线教育、云游戏等强实时互动场景 |
| DASH | 国际标准化的自适应码率协议，和 HLS 类似，基于 HTTP 分片，支持多种编码 | 3-10s，LL-DASH 1-3s | 无原生支持，需 dash.js+MSE 实现 | 编码无限制，支持 H.265/AV1，ABR 能力更强 | 苹果生态兼容性差，国内 CDN 支持度低 | 海外点播/直播，多编码自适应场景 |

##### 进阶加分点

-   选型核心逻辑：延迟要求越高，越倾向 WebRTC；兼容性要求越高，越倾向 HLS；国内直播平衡延迟与兼容性，选 HTTP-FLV。
-   补充：HTTP-FLV 和 HLS 的核心差异，HLS 是分片文件式传输，HTTP-FLV 是流式传输，所以 HTTP-FLV 延迟更低，而 HLS 兼容性更好。

### 面试题 2：Media Source Extensions (MSE) 是什么？核心作用、完整使用流程、适用场景？

#### 核心考点

前端自定义流媒体播放的底层原理，flv.js/hls.js 的核心实现基础。

#### 标准答案

##### 核心必答点

1.  **MSE 的核心定义与作用**
    MSE 全称 Media Source Extensions，是 W3C 标准的浏览器 API，**允许 JavaScript 动态创建媒体流，把音视频数据分片喂给 video/audio 标签进行播放**，打破了浏览器只能播放完整媒体文件的限制。
    核心作用：让前端可以自主控制媒体流的加载、解析、拼接，实现自定义流媒体协议播放（HTTP-FLV、HLS、DASH 等）、自适应码率、无缝切流、视频加密播放等能力，是前端流媒体播放器的核心底层。

2.  **MSE 完整使用流程（面试必背）**

    1.  检测兼容性：判断浏览器是否支持 MSE，`window.MediaSource`是否存在，以及对应编码格式的支持性。
    2.  创建 MediaSource 实例：`const mediaSource = new MediaSource();`
    3.  绑定 video 标签：把 MediaSource 实例的 object URL 赋值给 video 的 src，`video.src = URL.createObjectURL(mediaSource);`
    4.  监听 sourceopen 事件：MediaSource 和 video 绑定完成后触发，此时才能创建 SourceBuffer。
    5.  创建 SourceBuffer：根据媒体编码格式，创建对应的 SourceBuffer，`const sourceBuffer = mediaSource.addSourceBuffer('video/mp4; codecs="avc1.42E01E, mp4a.40.2"');`
    6.  拉取并喂入媒体数据：通过 AJAX/fetch 拉取音视频分片数据（ArrayBuffer 格式），调用`sourceBuffer.appendBuffer()`把数据喂入 SourceBuffer。
    7.  处理更新状态：监听`updateend`事件，确保上一次数据添加完成后，再喂入下一段数据，避免报错。
    8.  结束流：所有分片加载完成后，调用`mediaSource.endOfStream()`，通知浏览器媒体流结束，更新 duration。

3.  **核心适用场景**
    -   自定义流媒体播放：flv.js 播放 HTTP-FLV 流、hls.js 播放 HLS 流的底层核心。
    -   自适应码率（ABR）：动态切换不同码率的分片，无缝切换不卡顿。
    -   视频加密播放：前端解密加密的媒体分片后，再喂入 MSE 播放，实现 DRM 基础保护。
    -   视频拼接、预加载：把多个视频文件无缝拼接成一个流播放，实现无感知预加载。

##### 进阶加分点

-   核心坑点：`appendBuffer()`必须在 SourceBuffer 的`updating`为 false 时调用，否则会报错，必须通过`updateend`事件做流程控制。
-   内存优化：播放过程中，需调用`sourceBuffer.remove()`清理已播放过的 buffer 数据，避免内存暴涨。
-   编码匹配：`addSourceBuffer`的 codecs 必须和实际媒体数据的编码完全一致，否则会播放失败、花屏。

### 面试题 3：HLS 协议的工作原理？m3u8 文件结构？HLS 延迟如何优化？

#### 核心考点

点播/直播最通用协议的底层理解，业务优化能力。

#### 标准答案

##### 核心必答点

1.  **HLS 核心工作原理**
    HLS 全称 HTTP Live Streaming，是苹果公司推出的基于 HTTP 的自适应码率流媒体协议。
    核心逻辑：**把完整的音视频流，切分成一个个时长固定的 TS（Transport Stream）小分片文件，通过一个 m3u8 格式的索引文本文件，管理所有 TS 分片的地址、时长、码率等信息**。
    播放流程：

    1.  播放器先请求下载 m3u8 索引文件，解析出 TS 分片列表。
    2.  按顺序逐个下载 TS 分片文件。
    3.  把下载完成的 TS 分片，依次喂给解码器进行播放。
    4.  直播场景下，播放器会定时重新请求 m3u8 文件，更新最新的 TS 分片列表，实现持续播放。

2.  **m3u8 文件核心结构**
    m3u8 是基于 UTF-8 的文本文件，以`#EXTM3U`开头，通过#EXT 开头的标签定义配置，核心标签如下：

    -   基础标签：`#EXTM3U`（文件头，必须在第一行）、`#EXT-X-VERSION`（HLS 协议版本）。
    -   分片配置：`#EXT-X-TARGETDURATION`（每个 TS 分片的最大时长，单位秒，标准 HLS 默认 10s）、`#EXTINF`（每个 TS 分片的实际时长，后面紧跟分片地址）。
    -   直播/点播区分：`#EXT-X-ENDLIST`（文件末尾有该标签，代表点播，所有分片已生成；无该标签，代表直播，会持续更新分片）。
    -   自适应码率标签：`#EXT-X-STREAM-INF`（定义不同码率、分辨率的子 m3u8 地址，实现 ABR）。
        示例（点播 m3u8）：

    ```
    #EXTM3U
    #EXT-X-VERSION:3
    #EXT-X-TARGETDURATION:10
    #EXTINF:10.0,
    segment_0.ts
    #EXTINF:10.0,
    segment_1.ts
    #EXTINF:5.0,
    segment_2.ts
    #EXT-X-ENDLIST
    ```

3.  **HLS 延迟核心优化方案**
    延迟根因：标准 HLS 的延迟 ≈ 分片时长 × 分片数量，优化核心是**减少分片时长、减少播放缓冲的分片数量、优化拉取策略**。
    标准优化方案：
    1.  缩短分片时长：把标准 10s 分片，缩短为 2-3s，是最直接的降延迟方案（注意：分片过短会增加请求量，弱网下卡顿率上升）。
    2.  采用低延迟 HLS（LL-HLS）：苹果官方的低延迟方案，支持分片级别的部分加载（字节范围请求），延迟可降到 1s 以内。
    3.  优化播放器缓冲策略：减少播放器预加载的分片数量，标准 HLS 默认预加载 3 个分片，可降到 1-2 个，平衡延迟与卡顿。
    4.  直播 GOP 优化：GOP 时长和分片时长对齐，确保每个分片都有 I 帧，播放器加载完一个分片即可立即播放，无需等待下一个 I 帧。
    5.  CDN 优化：开启 CDN 分片预推、边缘节点缓存，减少分片拉取的网络耗时。

##### 进阶加分点

-   避坑点：iOS Safari 对 HLS 分片时长有严格限制，分片时长过短会导致播放异常，最低不建议低于 1s。
-   进阶优化：开启 HLS 的 CMAF 分片，兼容 LL-DASH，实现单分片跨协议复用，进一步降低延迟。

### 面试题 4：HTTP-FLV 协议原理？和 HLS 的核心区别？flv.js 的实现原理？

#### 核心考点

国内直播主流方案的底层理解，开源播放器的核心实现逻辑。

#### 标准答案

##### 核心必答点

1.  **HTTP-FLV 核心原理**
    HTTP-FLV 是把 RTMP 协议的 FLV 格式媒体数据，封装在 HTTP 协议中，通过 HTTP 长连接进行流式传输的流媒体协议。
    核心逻辑：**客户端和服务端建立 HTTP 长连接，服务端持续向客户端推送 FLV 格式的音视频数据，客户端边接收数据边解析解码播放**，无需等待完整文件下载，实现低延迟直播。
    核心特点：基于 HTTP 1.1 的 chunked 分块传输，天然穿透防火墙，CDN 广泛支持，延迟比标准 HLS 低很多。

2.  **HTTP-FLV 与 HLS 的核心区别**
    | 对比维度 | HTTP-FLV | HLS |
    |---|---|---|
    | 传输方式 | 流式传输，HTTP 长连接持续推送数据 | 分片文件式传输，逐个下载完整的 TS 分片 |
    | 典型延迟 | 1-3s | 标准 HLS 3-10s，LL-HLS 1-3s |
    | 浏览器兼容性 | 无原生支持，需 flv.js+MSE | 全平台原生支持，尤其是 iOS Safari 全系 |
    | 内存占用 | 低，流式解析，无需缓存完整分片 | 相对高，需缓存完整 TS 分片 |
    | seek 能力 | 弱，直播场景基本无法 seek | 强，基于分片可精准 seek |
    | 弱网抗性 | 相对弱，TCP 长连接断流需重连 | 强，分片式传输，断连后可续传 |

3.  **flv.js 的核心实现原理**
    flv.js 是 B 站开源的前端播放器库，核心作用是让浏览器原生不支持的 HTTP-FLV 流，能在 HTML5 video 标签中播放。
    核心实现流程：
    1.  **流式拉取 FLV 数据**：通过 fetch/XMLHttpRequest 流式拉取 HTTP-FLV 的 FLV 二进制数据（ArrayBuffer 格式）。
    2.  **FLV 解封装**：解析 FLV 二进制数据，分离出其中的 H.264 视频编码数据和 AAC 音频编码数据，解析出音视频的时间戳、帧信息。
    3.  **MP4 封装（转封装）**：把分离出来的 H.264/AAC 裸流，重新封装成 ISO BMFF 格式（也就是 MP4 格式的分片片段，fMP4），因为 MSE 只支持 MP4 分片格式，不支持 FLV 格式。
    4.  **MSE 喂流播放**：把封装好的 fMP4 分片，通过 MSE 的 SourceBuffer.appendBuffer()，喂给 video 标签进行解码播放。
        一句话总结：**flv.js 的核心是「FLV 解封装 + MP4 重封装」，把浏览器不支持的 FLV 格式，转换成 MSE 支持的 MP4 格式，实现播放**。

##### 进阶加分点

-   核心优势：纯 JavaScript 实现，无需插件，性能开销低，和原生 video 标签无缝对接，支持直播追帧、低延迟模式。
-   进阶优化：flv.js 的低延迟模式，核心是动态调整 buffer 阈值，超过阈值就丢弃过期数据，追赶上最新的直播时间戳，降低延迟。

## 三、WebRTC 实时音视频专项（必考，中高级进阶）

### 面试题 1：WebRTC 是什么？核心能力、三大核心模块、适用场景？

#### 核心考点

WebRTC 体系认知，核心能力边界理解。

#### 标准答案

##### 核心必答点

1.  **WebRTC 核心定义**
    WebRTC 全称 Web Real-Time Communication，是谷歌开源、W3C 标准化的**网页实时通信技术**，提供了浏览器之间音视频采集、编码、传输、解码、渲染的全链路能力，无需任何插件，即可实现超低延迟的实时音视频通信。

2.  **三大核心模块（面试必背）**
    | 核心模块 | 核心 API | 核心作用 |
    |---|---|---|
    | 媒体捕获模块（MediaStream） | `getUserMedia()`、`getDisplayMedia()` | 负责音视频采集，获取摄像头、麦克风、屏幕共享的媒体流，支持分辨率、帧率、码率等参数配置 |
    | 点对点连接模块（RTCPeerConnection） | `RTCPeerConnection` | WebRTC 的核心，负责媒体流的编码、NAT 穿透、P2P 连接建立、音视频数据的实时传输、网络与带宽自适应、丢包恢复 |
    | 数据通道模块（RTCDataChannel） | `createDataChannel()` | 基于 P2P 连接，实现任意二进制/文本数据的超低延迟传输，不依赖服务器中转，支持可靠/不可靠传输模式 |

3.  **核心能力**

    -   全平台支持：现代浏览器（Chrome/Firefox/Safari/Edge）、移动端、小程序均支持。
    -   超低延迟：基于 UDP 传输，端到端延迟最低可达 100ms 以内，远低于 TCP 流媒体协议。
    -   内置音视频处理：内置 3A 算法（AEC 回声消除、ANS 噪声抑制、AGC 自动增益），解决实时通话的音频问题。
    -   强大的弱网抗性：内置 NACK/FEC/RTX 丢包重传机制、Jitter Buffer 抖动缓冲、动态码率自适应，弱网下保障通话流畅。
    -   支持 P2P 与服务器中转：既支持端到端直连，也支持 TURN 服务器中继，保障复杂网络环境下的连通性。

4.  **核心适用场景**
    1v1 视频/语音通话、多人视频会议、直播连麦互动、在线教育小班课、云游戏、远程桌面控制、实时数据传输、物联网实时监控等。

##### 进阶加分点

-   传输层核心：WebRTC 媒体流基于 SRTP（安全实时传输协议）传输，数据通道基于 SCTP over DTLS 传输，保障数据安全。
-   编码支持：视频默认支持 VP8/VP9/H.264，现代浏览器已支持 H.265/AV1；音频默认支持 OPUS/G.711。

### 面试题 2：1v1 WebRTC 视频通话的完整实现流程？

#### 核心考点

WebRTC 核心落地能力，全链路流程的理解程度。

#### 标准答案

##### 核心必答点

WebRTC 本身不定义信令协议，核心流程分为**信令服务准备、媒体捕获、SDP 媒体协商、ICE 候选交换、P2P 连接建立、媒体流传输渲染**6 大阶段，完整流程如下：

1.  **前置准备：搭建信令服务**
    信令服务是 WebRTC 通话的前提，作用是在两个客户端之间转发 SDP 协商信息、ICE 候选地址，因为两个浏览器无法直接发现对方。通常用 WebSocket 实现双向通信，客户端加入同一个房间，即可互相转发消息。

2.  **阶段 1：呼叫方与被叫方初始化，采集本地媒体流**

    -   呼叫方（发起端）与被叫方（接收端）均初始化`RTCPeerConnection`实例，配置 ICE 服务器（STUN/TURN 地址）。
    -   双方通过`navigator.mediaDevices.getUserMedia()`获取本地摄像头/麦克风的媒体流，把媒体流添加到`RTCPeerConnection`实例中（`addTrack()`），同时渲染到本地 video 标签。
    -   双方监听`ontrack`事件，用于接收对方的远程媒体流；监听`onicecandidate`事件，用于收集本机的 ICE 候选地址。

3.  **阶段 2：SDP 媒体协商（Offer/Answer 交换，核心环节）**
    SDP 是会话描述协议，包含了双方的媒体能力（编码、分辨率、码率）、传输地址、加密信息等，协商的目的是让双方达成一致的媒体配置。

    1.  呼叫方创建 Offer SDP：调用`createOffer()`方法，生成本地的 Offer SDP。
    2.  呼叫方设置本地 SDP：调用`setLocalDescription()`，把 Offer SDP 设置为本地会话描述。
    3.  呼叫方通过信令服务，把 Offer SDP 发送给被叫方。
    4.  被叫方接收 Offer SDP，调用`setRemoteDescription()`，把呼叫方的 Offer SDP 设置为远程会话描述。
    5.  被叫方创建 Answer SDP：调用`createAnswer()`方法，生成本地的 Answer SDP。
    6.  被叫方设置本地 SDP：调用`setLocalDescription()`，把 Answer SDP 设置为本地会话描述。
    7.  被叫方通过信令服务，把 Answer SDP 发送给呼叫方。
    8.  呼叫方接收 Answer SDP，调用`setRemoteDescription()`，把被叫方的 Answer SDP 设置为远程会话描述。
        至此，SDP 媒体协商完成。

4.  **阶段 3：ICE 候选交换与 NAT 穿透**
    ICE 是交互式连接建立协议，用于收集双方的所有可用地址（内网地址、公网映射地址、TURN 中继地址），找到最优的 P2P 通信路径。

    1.  双方在`setLocalDescription()`之后，会自动开始收集 ICE 候选地址，每收集到一个候选，就会触发`onicecandidate`事件。
    2.  双方通过信令服务，把自己的 ICE 候选地址，转发给对方。
    3.  双方接收到对方的 ICE 候选后，调用`addIceCandidate()`方法，把对方的候选地址添加到本地 RTCPeerConnection 中。
    4.  双方自动对所有候选地址进行连通性检测，找到一条最优的、可连通的网络路径，建立 P2P 连接。

5.  **阶段 4：媒体流传输与渲染**
    P2P 连接建立成功后，双方通过 SRTP 协议，开始实时传输音视频媒体流。

    -   接收方通过`ontrack`事件，接收到对方的媒体流，把媒体流绑定到远程 video 标签，完成渲染，实现双向通话。

6.  **阶段 5：通话结束，资源释放**
    通话结束时，双方调用`RTCPeerConnection.close()`关闭 P2P 连接，停止媒体流的所有轨道，释放摄像头/麦克风资源，关闭信令连接。

##### 进阶加分点

-   核心坑点：SDP 协商必须遵循「Offer-Answer」的严格顺序，不能乱序；ICE 候选交换必须在 SDP 协商开始后才能进行，否则会失效。
-   进阶优化：Trickle ICE（涓流 ICE），也就是边收集 ICE 候选边转发，而不是等所有候选收集完成再转发，大幅缩短连接建立时间。

### 面试题 3：ICE/STUN/TURN 协议分别是什么？在 WebRTC 中的作用？NAT 穿透的原理？

#### 核心考点

WebRTC 连通性核心，难点考点，网络层原理理解。

#### 标准答案

##### 核心必答点

1.  **核心定义与层级关系**
    ICE 是 WebRTC 连接建立的核心框架，STUN 和 TURN 是 ICE 框架中的两个核心工具协议，三者配合解决复杂网络环境下的端到端连通性问题。

2.  **各协议的核心作用**

    -   **ICE（Interactive Connectivity Establishment，交互式连接建立）**
        是一个综合的 NAT 穿透框架，不是单一协议。核心作用是**收集客户端所有可用的网络地址（候选地址），按优先级排序，通过连通性检测，找到一条最优的、能实现端到端通信的网络路径**。
        ICE 收集的候选地址分为 3 类，优先级从高到低：

        1.  主机候选：客户端内网的本地 IP 地址。
        2.  服务器反射候选：通过 STUN 服务器获取的客户端公网映射 IP 地址。
        3.  中继候选：TURN 服务器分配的中继 IP 地址。
            ICE 会优先尝试主机候选直连，失败则尝试 STUN 反射候选，最后兜底用 TURN 中继候选，保障 100%的连通性。

    -   **STUN（Session Traversal Utilities for NAT，NAT 会话穿越工具）**
        核心作用：**帮助客户端获取自己的公网 IP 地址和端口，实现 NAT 穿透**。
        工作原理：

        1.  客户端向公网的 STUN 服务器发送请求。
        2.  STUN 服务器收到请求后，会把请求中携带的「客户端公网 IP+端口」，返回给客户端。
        3.  客户端拿到自己的公网映射地址后，把这个地址通过信令服务发给对方，双方即可通过这个公网地址，实现 P2P 直连。
            适用场景：绝大多数家用宽带、4G/5G 网络的锥形 NAT 环境，可通过 STUN 实现穿透。

    -   **TURN（Traversal Using Relays around NAT，中继式 NAT 穿越）**
        核心作用：**STUN 穿透失败时的兜底方案，通过 TURN 服务器进行媒体数据中继转发，保障端到端连通性**。
        工作原理：
        1.  客户端和 TURN 服务器建立连接，TURN 服务器给客户端分配一个中继地址。
        2.  客户端把中继地址通过信令服务发给对方，对方把媒体数据发送到这个中继地址。
        3.  TURN 服务器把收到的媒体数据，转发给对应的客户端，实现双向通信。
            适用场景：对称 NAT、企业内网、防火墙限制等无法实现 P2P 直连的复杂网络环境。

3.  **NAT 穿透的核心原理**
    NAT（网络地址转换）是路由器的核心功能，把内网的多个设备，映射到同一个公网 IP 地址的不同端口，解决公网 IP 地址不足的问题，同时也阻挡了外网主动向内网发起的连接，这就是 P2P 直连的核心障碍。
    NAT 穿透的核心逻辑：**让内网的两个客户端，都主动向对方的公网映射地址发送数据包，在各自的 NAT 设备上留下「访问记录」，NAT 设备就会把对方发来的数据包，转发到对应的内网设备上，实现穿透**。
    举个通俗的例子：两个在不同房间的人，都不能主动开门，只能通过门口的保安（NAT）传递消息。STUN 服务器帮他们拿到了对方门口保安的地址，两人同时让自己的保安给对方保安送消息，保安看到对方送来的消息，就会放行，两人就能直接通信了。

##### 进阶加分点

-   核心区别：STUN 只负责获取公网地址，不参与媒体数据转发，带宽成本为 0；TURN 需要全程转发媒体数据，服务器带宽成本极高，所以仅作为兜底方案。
-   NAT 类型：锥形 NAT（全锥、受限锥、端口受限锥）均可通过 STUN 穿透，对称 NAT 无法通过 STUN 穿透，必须用 TURN 中继。

## 四、编解码与媒体处理进阶（中高级高频）

### 面试题 1：视频编码的基本原理？I 帧/P 帧/B 帧的区别与作用？GOP 是什么？

#### 核心考点

音视频底层基础，编码原理的核心理解。

#### 标准答案

##### 核心必答点

1.  **视频编码的核心原理**
    视频本质是连续的静态图片（帧），按固定帧率播放形成动态画面。原始视频数据量极大（1080P 30 帧视频，1 秒原始数据约 370MB），无法直接存储和传输。
    视频编码的核心原理：**利用视频的空间冗余、时间冗余、视觉冗余，通过压缩算法，去除冗余数据，大幅降低视频体积，同时尽可能保留人眼可感知的画质**。

    -   空间冗余：单张图片内相邻像素的颜色、亮度高度相似，可压缩（帧内压缩）。
    -   时间冗余：相邻帧之间的画面内容高度相似，只有少量变化，可压缩（帧间压缩）。
    -   视觉冗余：人眼对高频细节、色彩变化的敏感度低于亮度变化，可丢弃部分人眼无法感知的信息。

2.  **I 帧/P 帧/B 帧的核心区别与作用**
    视频编码把帧分为 3 类，是帧间压缩的核心，也是 H.264/H.265 等编码的基础：
    | 帧类型 | 全称 | 核心原理 | 压缩率 | 解码依赖 | 核心作用 |
    |---|---|---|---|---|---|
    | I 帧 | 帧内编码帧/关键帧 | 仅对当前帧做帧内压缩，不参考其他帧，类似一张完整的 JPG 图片 | 最低（体积最大） | 无，可独立解码 | 1. 作为随机访问（seek）的入口，seek 必须定位到 I 帧；2. 作为 GOP 的起始帧，为 P/B 帧提供参考；3. 丢包后画面恢复的基准 |
    | P 帧 | 前向预测帧 | 参考前面的 I 帧/P 帧，只编码和参考帧之间的差异数据 | 中等（体积约为 I 帧的 1/10） | 依赖前面的 I/P 帧，无法独立解码 | 大幅压缩视频体积，是视频帧的主要组成部分 |
    | B 帧 | 双向预测帧 | 同时参考前面和后面的 I/P 帧，编码前后帧之间的差异数据 | 最高（体积约为 I 帧的 1/50） | 依赖前后的 I/P 帧，无法独立解码 | 极致压缩视频体积，提升压缩率 |

3.  **GOP 的核心定义与作用**
    GOP 全称 Group of Pictures，也就是**画面组**，指的是**两个相邻 I 帧之间的所有帧组成的序列**，一个 GOP 就是一个独立的解码单元。
    核心参数：GOP 长度，也就是两个 I 帧之间的帧数/时长。比如 30 帧/秒的视频，GOP 长度 30，就是 1 秒一个 I 帧。
    核心影响：
    -   GOP 越长：I 帧越少，视频压缩率越高，体积越小，延迟越高，seek 越不精准，丢包后画面恢复越慢。
    -   GOP 越短：I 帧越多，视频体积越大，延迟越低，seek 越精准，弱网下画面恢复越快，抗丢包能力越强。
        典型场景：直播场景 GOP 时长通常设为 1-2 秒，降低延迟，提升 seek 和抗丢包能力；点播场景 GOP 时长通常设为 5-10 秒，提升压缩率，降低体积。

##### 进阶加分点

-   避坑点：B 帧会增加编码和解码的延迟，因为需要等待后面的参考帧解码，所以实时直播、WebRTC 场景，通常会关闭 B 帧，只用 I 帧和 P 帧，降低延迟。
-   进阶知识：IDR 帧是特殊的 I 帧，IDR 帧之后的所有帧，都不能参考 IDR 帧之前的帧，保障 seek 到 IDR 帧时，不会出现画面花屏，是随机访问的核心。

### 面试题 2：H.264/H.265(HEVC)/AV1/VP9 编码格式的优缺点、兼容性、适用场景对比？

#### 核心考点

视频编码选型能力，业务场景适配能力。

#### 标准答案

##### 核心必答点

核心对比表（面试必答）：
| 编码格式 | 推出方 | 压缩率（同画质下体积） | 浏览器兼容性 | 编码/解码复杂度 | 版权/专利 | 核心适用场景 |
|---|---|---|---|---|---|---|
| H.264(AVC) | ITU-T/ISO | 基准，100% | 全平台全浏览器原生支持，兼容性拉满 | 低，软编软解性能开销小 | 有专利费，20 年内已广泛普及，终端授权成本极低 | 全场景通用，点播、直播、WebRTC、短视频，是兼容性要求高的场景的首选 |
| H.265(HEVC) | ITU-T/ISO | 比 H.264 提升 50%（同画质体积减半） | 移动端兼容性好，PC 端 Chrome/Firefox 仅支持硬解，Safari 全支持 | 中高，编码复杂度是 H.264 的 2-3 倍 | 专利池混乱，专利费高，商业使用有版权风险 | 短视频、点播、安防监控，对存储/带宽成本敏感，且兼容性能覆盖的场景 |
| VP9 | 谷歌 | 比 H.264 提升 40-50% | Chrome/Firefox 全支持，Safari 14.1+支持，国产浏览器支持一般 | 高，编码复杂度高于 H.265 | 完全开源免费，无专利费 | 海外 Chrome 生态的点播/直播，YouTube 的主力编码，无版权成本的场景 |
| AV1 | AOMedia（谷歌/苹果/微软等） | 比 H.265 提升 30%，比 H.264 提升 70% | 现代浏览器新版均支持，低版本浏览器不支持 | 极高，编码复杂度是 H.265 的 5-10 倍，软编性能开销极大 | 完全开源免费，无专利费 | 未来主流编码，长视频点播、对带宽成本极致敏感的场景，目前仅适合超大型平台使用 |

##### 进阶加分点

-   选型核心逻辑：**兼容性优先选 H.264，带宽/存储成本优先选 H.265，无版权成本优先选 VP9/AV1**。
-   业务坑点：H.265 在 PC 端 Chrome 浏览器，仅支持硬件解码，若用户电脑显卡不支持 H.265 硬解，会导致播放失败，需做编码降级兼容。
-   WebRTC 场景：H.264 是唯一全浏览器兼容的编码，VP9 在 Chrome 生态支持良好，H.265 仅 Safari 和部分新版浏览器支持。

## 五、性能优化与兼容性（必考，全级别通用）

### 面试题 1：直播流秒开优化的完整方案有哪些？

#### 核心考点

直播核心体验指标优化，全链路优化能力。

#### 标准答案

##### 核心必答点

直播秒开的核心指标是「首帧时间」，指的是用户点击播放到看到第一帧画面的时间，优化核心是**减少首帧前的所有耗时环节，让播放器最快拿到可解码的 I 帧数据**。
完整优化方案分为前端、服务端/CDN、协议三大维度：

1.  **前端优化（可控性最高，优先落地）**

    -   预加载策略：
        1.  页面预加载：用户进入直播列表页，提前加载首屏直播间的 m3u8/flv 地址的首分片，提前完成 DNS 解析、TCP 连接。
        2.  实例预创建：提前创建 video 标签和播放器实例，提前完成 MSE 初始化，减少播放前的初始化耗时。
    -   播放器配置优化：
        1.  调整缓冲阈值：降低播放器首帧播放所需的缓冲数据量，默认需要缓冲 500ms-1s 数据，可降到 200-300ms，拿到 I 帧即可立即解码播放。
        2.  精准 seek 到最新 I 帧：直播播放时，直接 seek 到直播流的最新关键帧位置，跳过历史缓冲数据，直接播放最新内容。
        3.  关闭不必要的初始化逻辑：播放前不执行非必要的 API 调用、事件绑定，优先执行播放核心逻辑。
    -   解码与渲染优化：
        1.  开启硬件解码：优先使用 H.264 编码，开启浏览器硬件加速，降低解码耗时。
        2.  提前设置 video 属性：提前设置好`playsinline`、`crossorigin`、`muted`等属性，避免播放时属性变更导致重新加载。
        3.  复用 video 实例：直播间切换时，复用同一个 video 标签，避免重复创建销毁 DOM 带来的耗时。

2.  **服务端/CDN 优化（核心瓶颈，决定优化上限）**

    -   GOP 缓存优化：CDN 边缘节点缓存最新的 1-2 个 GOP 数据，用户请求直播流时，立即返回缓存的最新 GOP 数据，播放器拿到 I 帧即可立即解码播放，无需等待下一个 I 帧，这是秒开优化最核心的手段。
    -   首分片优化：把直播流的第一个分片，强制以 I 帧开头，确保播放器拿到第一个分片就能解码播放，无需等待后续数据。
    -   网络优化：
        1.  开启 HTTP/2/HTTP/3，复用连接，减少 TCP 握手、TLS 握手耗时。
        2.  CDN 智能调度，把用户调度到最近的边缘节点，降低网络延迟。
        3.  提前 DNS 预解析，页面添加`<link rel="dns-prefetch" href="直播CDN域名">`，提前完成 DNS 解析。

3.  **协议与编码优化**
    -   协议选型：优先选择 HTTP-FLV/LL-HLS，延迟更低，秒开效果更好，标准 HLS 分片时长过长，秒开效果差。
    -   缩短 GOP 时长：把 GOP 时长从默认 5-10s，缩短到 1-2s，确保播放器能快速拿到 I 帧，平衡秒开效果与码率。
    -   编码优化：使用 H.264 Baseline Profile，降低解码复杂度，提升解码速度，首帧出图更快。

##### 进阶加分点

-   兜底方案：对于弱网用户，提供低码率、低分辨率的直播流，首屏先播放低码率流，播放成功后再无缝切换到高码率流，提升秒开成功率。
-   数据指标：秒开优化的核心是数据量化，需埋点统计 DNS 耗时、TCP 连接耗时、首包耗时、首帧耗时、秒开率（1s 内首帧占比），针对性优化瓶颈环节。

### 面试题 2：移动端音视频播放的兼容性坑与解决方案？

#### 核心考点

线上兼容性问题处理能力，移动端业务落地经验。

#### 标准答案

##### 核心必答点

移动端音视频的核心兼容性问题，集中在 iOS Safari、微信内置浏览器、安卓碎片化浏览器，核心坑点与解决方案如下：

1.  **iOS Safari 核心坑点与解决方案**

    -   坑点 1：自动全屏问题，video 标签播放时会自动弹出系统全屏播放器，无法内联播放。
        解决方案：给 video 标签添加`playsinline` + `webkit-playsinline`属性，同时关闭`airplay`属性，iOS 10+支持内联播放。
    -   坑点 2：自动播放限制严格，即使静音，无用户交互也无法自动播放。
        解决方案：严格遵循自动播放策略，默认静音播放，用户交互后再开启声音；在用户点击进入页面的前置操作中，提前触发一次播放操作，获取播放权限。
    -   坑点 3：不支持 MSE 播放 HTTP-FLV 流，flv.js 在 iOS Safari 无法使用。
        解决方案：iOS 端统一使用 HLS 协议播放，通过 UA 判断，iOS 自动切换到 HLS 流地址。
    -   坑点 4：视频层级最高，无法被 DOM 元素覆盖，z-index 无效。
        解决方案：iOS Safari 中，video 标签是系统级渲染，层级最高，若需覆盖 UI，需使用`webkit-video-playsinline`内联播放，同时避免在视频播放时做 fixed 定位的弹窗，或使用 canvas 把视频渲染出来，再覆盖 DOM。
    -   坑点 5：`preload`属性失效，无法预加载视频数据。
        解决方案：iOS Safari 为了节省用户流量，会忽略`preload="auto"`，只能通过用户交互后提前调用`load()`方法加载，或提前加载首分片数据。

2.  **微信内置浏览器核心坑点与解决方案**

    -   坑点 1：微信 X5 内核（安卓）自动全屏，同层播放问题。
        解决方案：给 video 标签添加`x5-playsinline`、`x5-video-player-type="h5"`、`x5-video-player-fullscreen="false"`属性，开启 X5 内核的 H5 同层播放器。
    -   坑点 2：微信 iOS 端，视频播放会被劫持，自动调用腾讯的播放器，无法自定义 UI。
        解决方案：开启`playsinline`内联播放，同时避免视频 src 直接赋值，通过 MSE 方式加载，或使用微信 JSSDK 的视频接口适配。
    -   坑点 3：音频播放，页面切后台后会暂停，无法继续播放。
        解决方案：使用 Web Audio API 播放音频，或配合微信 JSSDK 的音频接口，同时监听`visibilitychange`事件，页面恢复可见时重新播放。

3.  **安卓端通用坑点与解决方案**

    -   坑点 1：机型碎片化，部分低端机型不支持 H.265 编码，播放失败、花屏。
        解决方案：优先使用 H.264 Baseline Profile 编码，做编码兼容性检测，不支持 H.265 的机型自动降级到 H.264 流。
    -   坑点 2：有声音无画面，黑屏问题。
        解决方案：1. 确保视频分片的每个关键帧都完整，避免 I 帧丢失；2. 关闭 B 帧，部分低端安卓机型不支持 B 帧解码；3. 确保 video 标签在 DOM 树中，且有宽高，不可 visibility:hidden。
    -   坑点 3：多个 video 实例同时播放，出现音频冲突、播放卡顿。
        解决方案：移动端同一时间只保留一个活跃的 video 实例，其他视频暂停并释放资源，避免多个媒体实例同时占用解码器。

4.  **全平台通用移动端解决方案**
    -   统一播放器内核：使用成熟的开源播放器（xgplayer、video.js），内置了全平台的兼容性适配，避免重复踩坑。
    -   UA 判断适配：通过 UA 判断系统、浏览器类型，针对性设置属性、切换播放协议、降级编码。
    -   异常事件兜底：监听所有播放异常事件，出现播放失败时，自动降级重试，比如 HTTP-FLV 失败自动切换到 HLS 流。

## 六、业务实战高频题

### 面试题 1：如何实现抖音/快手类短视频的上下滑动切换、预加载、预播放？核心优化点有哪些？

#### 核心考点

复杂业务场景的落地能力，性能与体验的平衡优化。

#### 标准答案

##### 核心必答点

短视频上下滑动的核心体验是「滑动即播放，无等待、无卡顿、无黑屏」，核心实现方案分为**滑动架构、预加载策略、预播放策略、内存与性能优化**四大模块：

1.  **滑动架构设计**

    -   采用 RecyclerView/ListView 思想的虚拟滚动列表，仅渲染当前播放项、上一项、下一项 3 个 DOM 节点，其余项用占位符替代，避免大量 video 实例同时存在，导致内存暴涨、页面卡顿。
    -   滑动容器使用 transform 滚动，配合 scroll 事件/IntersectionObserver 监听元素的可见比例，当视频项完全进入视口（100%可见）时，触发播放，离开视口时触发暂停与资源释放。
    -   滑动防抖：滑动过程中不执行播放/暂停操作，等待滑动结束、元素稳定后，再执行播放逻辑，避免频繁切换播放状态导致的性能问题。

2.  **核心预加载策略**
    预加载的核心是「用户看到下一个视频前，已经提前加载好首帧和关键数据，滑动后立即播放」，平衡带宽与体验。

    -   分级预加载：
        1.  一级预加载（当前播放项）：完整加载当前视频，保障播放流畅。
        2.  二级预加载（下一个/上一个视频）：提前加载视频的前 20%-30%数据，或前 1-2 个 GOP 分片，确保滑动后能立即播放。
        3.  三级预加载（列表后续项）：仅预加载视频的元数据、封面图，不加载视频数据，节省带宽。
    -   预加载实现方案：
        1.  分片式预加载：HLS 视频，提前下载下一个视频的前 1-2 个 TS 分片，缓存到内存中，播放时直接喂入 MSE。
        2.  视频对象预加载：创建隐藏的 video 标签，设置`preload="metadata"`，提前加载下一个视频的元数据和首帧，同时设置`crossorigin`属性，避免跨域问题。
        3.  分片缓存池：建立全局的视频分片缓存池，已下载的分片不会重复下载，滑动回退时直接使用缓存数据。

3.  **预播放策略**

    -   无声预播放：下一个视频预加载完成后，在隐藏的 video 标签中，静音预播放首帧，解码完成后暂停，等待滑动进入视口时，立即取消静音、恢复播放，实现零等待起播。
    -   播放状态切换：当前视频完全离开视口时，立即暂停播放，停止加载，释放 buffer 数据；目标视频完全进入视口时，立即从预播放位置开始播放，无缝衔接。
    -   起播优化：所有视频统一 GOP 时长（1s），每个视频的开头都是 I 帧，预加载到 I 帧即可立即解码播放，首帧出图时间控制在 100ms 以内。

4.  **核心优化点**
    -   内存优化：
        1.  同一时间仅保留 1 个播放中的 video 实例，其余预加载的 video 实例仅保留 1-2 个，超出的立即销毁，释放资源。
        2.  视频播放完成后，立即调用`video.src = ''` + `video.load()`，清空视频资源，释放内存。
        3.  MSE 播放时，定时清理已播放的 buffer 数据，避免内存持续上涨。
    -   流量优化：
        1.  弱网环境下，自动降低预加载的分片数量，仅预加载首分片，优先保障当前播放视频的流畅度。
        2.  WIFI 环境下，预加载更多分片，提升体验；移动数据环境下，减少预加载，节省用户流量。
    -   体验优化：
        1.  首帧占位：用视频的封面图作为 video 标签的 poster，预加载完成前显示封面，避免黑屏。
        2.  滑动过程中，禁止视频播放，避免画面闪烁、音频混乱。
        3.  播放失败兜底：预加载失败的视频，滑动到该位置时，自动重试加载，同时显示加载动画。

### 面试题 2：音视频播放出现黑屏/花屏/绿屏、有声音无画面的排查思路与解决方案？

#### 核心考点

线上问题排查能力，底层原理的理解与落地。

#### 标准答案

##### 核心必答点

先给核心排查逻辑：**先区分是前端渲染问题、解码问题，还是源文件/流的问题，再按从易到难的顺序排查**。

1.  **有声音无画面（最常见）排查与解决方案**
    有声音说明音频流解码正常，问题集中在视频流、解码、渲染环节。

    -   排查 1：视频编码与浏览器兼容性问题
        原因：视频使用了浏览器不支持的编码格式（比如 H.265/AV1，部分浏览器/低端机型不支持）、编码 Profile 过高（比如 H.264 High Profile，低端安卓机型不支持）、包含 B 帧，解码器无法解码视频流。
        解决方案：
        1.  优先使用 H.264 Baseline/Main Profile 编码，关闭 B 帧，兼容全平台。
        2.  做编码兼容性检测，不支持 H.265 的机型，自动降级到 H.264 流。
    -   排查 2：视频流缺少关键帧（I 帧）
        原因：直播流加载时，第一个分片没有 I 帧，解码器无法完成初始化解码，只有音频能正常解码，导致有声音无画面。
        解决方案：
        1.  服务端确保每个分片的开头都是 I 帧，CDN 缓存最新的 GOP 数据，播放器请求时先返回完整的 I 帧。
        2.  播放器检测到无 I 帧时，自动请求下一个包含 I 帧的分片，或重新加载流。
    -   排查 3：video 标签渲染问题
        原因：video 标签宽高为 0、display:none、visibility:hidden、脱离文档流，浏览器不会渲染画面；z-index 层级过低，被其他元素遮挡。
        解决方案：
        1.  确保 video 标签有明确的宽高，在 DOM 树中正常渲染，display 不为 none。
        2.  检查元素层级，避免被其他 DOM 元素遮挡，iOS 端需确保内联播放正常。
    -   排查 4：MSE 封装问题
        原因：flv.js/hls.js 转封装时，视频轨的时间戳异常、SPS/PPS 参数错误，导致解码器无法解码视频帧。
        解决方案：
        1.  检查播放器日志，是否有视频解码错误、时间戳溢出的报错。
        2.  升级播放器版本，开启播放器的时间戳矫正、错误帧跳过功能。

2.  **黑屏/花屏/绿屏排查与解决方案**

    -   排查 1：关键帧丢失、帧数据损坏
        原因：网络波动导致视频帧数据丢失、损坏，解码器无法正常解码，出现花屏/绿屏；I 帧丢失后，P/B 帧无参考帧，无法解码，出现黑屏。
        解决方案：
        1.  播放器监听`waiting`/`error`事件，检测到帧数据异常时，自动请求关键帧，或刷新直播流。
        2.  弱网环境下，开启 FEC 前向纠错，降低丢包率；缩短 GOP 时长，快速恢复画面。
    -   排查 2：解码性能瓶颈
        原因：4K/高码率视频，软解码性能不足，导致解码卡顿、花屏；多个视频同时解码，解码器资源耗尽。
        解决方案：
        1.  开启硬件解码，使用浏览器支持的硬解编码格式。
        2.  移动端限制同时解码的视频数量，同一时间仅解码一个视频。
        3.  低端机型自动降级到低码率、低分辨率视频流。
    -   排查 3：色彩空间/格式不兼容
        原因：视频的色彩空间（比如 YUV 4:2:2 10bit），浏览器/显卡不支持，导致渲染异常，出现绿屏/花屏。
        解决方案：
        1.  转码时统一使用 YUV 4:2:0 8bit 色彩格式，兼容所有浏览器和设备。
    -   排查 4：浏览器/显卡硬件加速异常
        原因：浏览器硬件加速开启异常，显卡驱动问题，导致视频渲染异常。
        解决方案：
        1.  引导用户关闭再重新开启浏览器硬件加速，更新显卡驱动。
        2.  播放器兜底方案，检测到渲染异常时，自动切换到软解码模式。

3.  **通用排查步骤（面试必答）**
    1.  源文件验证：用原生播放器（VLC）播放视频源/流，确认是否源文件本身有问题，排除服务端/推流问题。
    2.  兼容性验证：在不同浏览器、不同设备上测试，确认是否是特定机型/浏览器的兼容性问题。
    3.  日志排查：打开播放器的 debug 日志，查看是否有解码错误、网络错误、MSE 报错、跨域问题。
    4.  编码格式检测：用 ffmpeg 查看视频的编码格式、Profile、GOP 结构、帧信息，确认是否符合浏览器支持规范。
    5.  渲染层排查：检查 video 标签的 DOM 属性、CSS 样式，确认是否是渲染层面的问题。
