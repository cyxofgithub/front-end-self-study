## 能够熟练运用 JS/AJAX/HTML5/CSS/AS 等前端开发技术构建高性能 Web 应用程序

### AS

#### [什么是 AssemblyScript？它和 TypeScript、JavaScript 有什么核心区别？](../../../../性能与浏览器/WebAssembly/03_AssemblyScript面试题.md#1-assemblyscript-是什么和-typescriptjavascript-有什么区别)

AssemblyScript 是语法接近 TypeScript、但直接编译到 Wasm 的静态类型语言，不是能运行任意 TS/JS 的编译器。

#### [为什么选择用 AssemblyScript 开发 WebAssembly？相比其他 Wasm 开发方案有什么优势？](../../../../性能与浏览器/WebAssembly/03_AssemblyScript面试题.md#2-为什么选-assemblyscript-开发-wasm)

AS 的优势是 TS 团队学习和迁移成本低，适合独立计算内核；复用原生库选 C/C++，复杂长期核心库常优先评估 Rust。

#### [JS 和 Wasm 之间怎么传递数据？有哪些数据类型限制？数据传参会带来什么性能损耗？](../../../../性能与浏览器/WebAssembly/03_AssemblyScript面试题.md#3-js-和-wasm-怎么传数据)

单个数值（如 `i32/f64`）可直接传递；它们也叫标量，即一个值，不是数组或对象。字符串、数组和对象通常要先写入线性内存，再传指针和长度；损耗主要来自跨边界调用、分配、拷贝和编解码，所以 API 应该批量化。

#### [AssemblyScript 的内存管理机制是怎样的？和 JS 的垃圾回收有什么不同？](../../../../性能与浏览器/WebAssembly/03_AssemblyScript面试题.md#4-assemblyscript-怎么管理内存)

是，默认情况下两者都会自动回收对象。JS GC 管理 JS 引擎堆；AS 运行时的 GC 管理 Wasm 线性内存中的 AS 对象，两套 GC 相互独立。Wasm 本身不会自动回收线性内存；JS 长期持有 AS 指针时还要正确 `pin/unpin`。

#### [什么业务场景适合用 Wasm 做性能优化？飞书文档里哪些能力适合用 AS 重构？](../../../../性能与浏览器/WebAssembly/03_AssemblyScript面试题.md#5-什么业务适合-wasm飞书文档哪些能力可候选)

适合 CPU 密集、数据可批处理、不依赖 DOM 的热点；文档中可评估导入导出解析、CRDT 编解码/合并、索引、diff、表格公式和媒体处理。

#### [怎么调试和 profiling AssemblyScript 代码？怎么评估它的性能收益？](../../../../性能与浏览器/WebAssembly/03_AssemblyScript面试题.md#6-怎么调试profiling-和评估收益)

用 source map/`.wat`/DevTools 定位，基准要比较 release 构建的端到端 p50/p95/p99，并统计初始化、胶水拷贝、内存、包体和正确性。

## 飞书业务场景准备

### [多人编辑文档技术原理](../../../../编辑器/在线文档协同/code/README.md#技术原理简述)

核心链路是“本地立即编辑、增量同步、确定性合并、服务端转发与持久化”：用户输入先变成编辑器 transaction，并立即更新本地视图；协同适配层再把 transaction 转为 OT operation 或 CRDT update，通过 WebSocket 按 `docId` 房间发送。服务端负责鉴权、路由、广播、增量日志和快照；其他客户端收到 update 后去重、合并并映射回编辑器视图。

正文内容与在线状态要走两条链路：正文 update 必须可靠、幂等、可补洞，光标和在线用户等 awareness 数据可以限频和丢弃。断线重连时通过版本号/state vector 找出缺失增量，积压过大则加载“快照 + 后续增量”；OT 由服务端顺序化并转换并发操作，CRDT 则依靠稳定 ID、因果关系和确定性规则使各副本最终收敛。

### [针对飞书文档这类大型富文本应用，常见的性能瓶颈有哪些？你会从哪些维度做优化？](../../../../编辑器/大型富文本性能与稳定性.md#1-大型富文本应用的常见瓶颈)

瓶颈包括输入 transaction、文档树 diff/normalize、DOM/Layout/Paint、Decorations/插件、协同合并、网络和内存。我会先分阶段埋点，再围绕 INP、transaction p95、帧耗时、DOM 数和 heap 定向优化。

### [面对十万字级别的大文档，怎么解决渲染卡顿、滚动掉帧、内存占用过高的问题？](../../../../编辑器/大型富文本性能与稳定性.md#2-十万字文档怎么优化)

模型层保留完整文档，视图层按 block 分片和虚拟化，只挂载视口附近 DOM；变更、装饰和索引增量更新。撤销栈与缓存设上限，快照压缩、图片懒加载，并保证 Selection/IME 在虚拟化下正确。

### [你了解在线协同编辑的 OT 和 CRDT 算法吗？核心原理和区别是什么？](../../../../编辑器/在线文档协同/编辑器多人协作冲突原理.md#ot-vs-crdt-选型决策图)

OT 是“改操作”：对并发操作做 transform，常依赖中心服务与版本号。CRDT 是“改数据结构”：用稳定 ID、因果关系和确定性规则让 update 可交换、幂等并最终收敛；离线多端更友好，但元数据和压缩成本更高。

### [多人实时协同场景下，怎么解决编辑冲突？怎么保证最终一致性？](../../../../编辑器/在线文档协同/编辑器多人协作冲突原理.md#异常场景补充全播时某个节点网络异常)

本地操作先乐观应用，再通过 OT transform 或 CRDT 确定性规则解决并发冲突。还要用 update ID/版本向量去重补洞、幂等 apply、断线重连、快照 + 增量恢复和确定性 schema 规则保证收敛。

### [主流的富文本编辑器（ProseMirror/Slate/Draft.js）有什么区别？各有什么优缺点？](../../../../编辑器/编辑器框架.md#核心对比面试选型高频)

ProseMirror 强 schema、transaction/plugin 成熟，学习曲线陡但适合复杂文档和平台化；Slate 是 React 友好的 JSON 节点树，灵活易上手但复杂约束靠团队沉淀；Draft.js 的 block/entity 模型适合存量和简单编辑器，新大型项目通常不首选。

### [多人同时编辑大文档时，怎么保证前端的流畅性和服务端的稳定性？](../../../../编辑器/大型富文本性能与稳定性.md#3-多人同时编辑时的前后端稳定性)

前端本地操作立即 apply，远端 update 按帧批量并做背压，awareness 限频可丢弃；服务端按 `docId` 分片保证文档内顺序，以幂等日志、快照、增量补洞、限流和热点隔离保证稳定。
