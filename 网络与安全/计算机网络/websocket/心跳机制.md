# 心跳机制介绍

> **一句话结论：** 心跳解决「TCP 半打开」——长连接可能已经被中间设备静默掐断、客户端却毫无感知；前端走**应用层 ping/pong**（浏览器 JS 发不了协议层 ping 帧），靠「连续 N 次没收到任何消息」主动判死，而不是傻等永远不来的 `onclose`。

---

## 一、为什么需要心跳

「连接还开着」是个假象，三个原因：

1. 中间 NAT 网关 / LB（如 Nginx `proxy_read_timeout` 默认 60s）会静默掐掉「长时间无数据」的连接，形成 **TCP 半打开**——客户端以为连着，对端早死了；
2. 要尽快发现对端崩溃（不发数据检测不出来）；
3. TCP 自带 keepalive 默认 2 小时、浏览器 JS 又调不了，不能依赖。

> **关键限制**：WebSocket 协议层有 ping/pong 帧，但**浏览器 JS 无法发送**，所以前端一律走**应用层心跳**（发一条 `{"type":"ping"}`，对端回 `{"type":"pong"}`）。mqtt.js 的 `keepalive` 参数由库代发协议层心跳，语义等价。

---

## 二、实现：连续 N 次没回音才判死

判死**不要等 `onclose`**——半打开连接永远不会触发它，必须靠「N 个周期没有任何入站消息」主动 `close()`，再交给重连逻辑。

```typescript
class Heartbeat {
  private timer = 0;
  private missed = 0;

  constructor(
    private send: () => void,          // 发 {"type":"ping"}
    private onDead: () => void,        // 判死 → 主动 close → 触发重连
    private readonly interval = 15000, // 心跳周期
    private readonly maxMissed = 3,    // 连续 3 次无 pong 判死
  ) {}

  start() {
    this.timer = window.setInterval(() => {
      if (++this.missed > this.maxMissed) { this.stop(); this.onDead(); return; }
      this.send();
    }, this.interval);
  }

  feedPong() { this.missed = 0; } // 收到任意消息都算活着：pong 或业务消息都 reset

  stop() { clearInterval(this.timer); }
}
```

**两个面试加分点**：

1. `feedPong()` 收到**任意消息**都清零——业务消息本身也证明链路活着，不必死等 pong；
2. 判死动作是 `close()` 而不是直接重连——统一从 `onclose` 走重连，避免双路径。

---

## 面试回答

> 心跳解决的是 TCP 半打开：长连接可能被 NAT 网关或 LB 静默掐断，客户端还以为连着。因为浏览器 JS 发不了 WebSocket 协议层的 ping 帧，所以走应用层心跳——定时发一条 ping，对端回 pong。判死不能等 onclose，半打开连接永远不会触发它，而是连续 N 个周期没收到任何消息就主动 close，再交给重连逻辑。细节上收到任意业务消息都算心跳有效、清零计数。
