# 强缓存与协商缓存核心对比表

| **对比维度**         | **强缓存**                                                      | **协商缓存**                                                                                                 |
| -------------------- | --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| 核心机制             | 客户端**本地自主判断**缓存是否有效，无需服务端参与              | 客户端携带缓存标识与服务端**双向验证**，由服务端判断资源是否更新                                             |
| 是否发送请求到服务端 | ❌ 完全不发送，本地直接读取缓存                                 | ✅ 发送请求，但仅传输验证标识，不传输完整资源                                                                |
| 核心控制字段         | 响应头：`Cache-Control`（HTTP/1.1 优先）、`Expires`（HTTP/1.0） | 响应头+请求头配对：<br>1. `ETag` / `If-None-Match`（优先级更高）<br>2. `Last-Modified` / `If-Modified-Since` |
| 典型状态码           | 200 OK (from disk cache / memory cache)                         | 命中缓存：304 Not Modified<br>资源更新：200 OK                                                               |
| 性能开销             | 极低（纯本地 IO 操作，无网络耗时）                              | 低（仅传输验证信息，无资源传输开销）                                                                         |
| 控制权归属           | 客户端主导（基于本地缓存规则判断）                              | 服务端主导（最终由服务端判定资源是否更新）                                                                   |
| 触发条件             | 1. 本地存在缓存<br>2. 缓存未超过 `max-age` / `Expires` 时间     | 1. 强缓存失效或被主动跳过（如 `no-cache`、F5 刷新）<br>2. 服务端配置了协商缓存标识字段                       |
| 缓存有效性更新       | 缓存有效期内永久有效，不会主动更新                              | 命中 304 后，会**更新强缓存的有效期**                                                                        |
| 适用场景             | 静态资源（如图片、CSS、JS），内容短期内不会变化                 | 频繁更新的静态资源，或需要精准控制缓存新鲜度的场景                                                           |
| 缺点                 | 缓存过期前无法获取服务端最新资源（需手动刷新）                  | 每次都要发起请求，有轻微的网络往返耗时                                                                       |
