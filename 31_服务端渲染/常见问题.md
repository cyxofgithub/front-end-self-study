### 一、基础概念与核心原理

#### 1. 什么是 SSR？它的核心目标是什么？

-   **定义**：SSR（Server-Side Rendering，服务端渲染）是指在服务端（而非客户端）完成 HTML 的生成，将完整的 HTML 页面返回给浏览器，后续页面交互再由客户端 JS 接管。
-   **核心目标**：解决**首屏加载慢**、**SEO 不友好**、**白屏时间长**等问题，同时提升用户体验和搜索引擎抓取效率。

#### 2. SSR 与 CSR（客户端渲染）的本质区别？

| 对比维度     | SSR（服务端渲染）                         | CSR（客户端渲染）                          |
| ------------ | ----------------------------------------- | ------------------------------------------ |
| 页面生成位置 | 服务端（Node.js）                         | 客户端（浏览器）                           |
| 首屏加载速度 | 快（直接返回 HTML，无需等待 JS 加载执行） | 慢（需先加载 JS，再动态生成页面）          |
| SEO 友好度   | 高（搜索引擎可直接解析 HTML 内容）        | 低（需依赖 JS 渲染，部分搜索引擎无法抓取） |
| 白屏时间     | 短（服务端已生成 HTML）                   | 长（白屏期间需等待 JS 执行）               |
| 初始加载资源 | 较大（需加载完整 HTML+服务端数据）        | 较小（仅加载 JS 和 API 请求）              |
| 页面交互体验 | 需依赖客户端 JS（水合后）                 | 完全由客户端 JS 驱动，交互更流畅           |

#### 3. SSR 的核心流程是什么？

1. 浏览器发起请求，服务端接收请求；
2. 服务端根据路由匹配对应的页面组件；
3. 服务端获取页面所需数据（如接口请求、数据库查询）；
4. 服务端将数据与组件结合，渲染生成完整的 HTML 字符串；
5. 服务端将 HTML 字符串返回给浏览器；
6. 浏览器接收 HTML 并解析渲染，同时客户端 JS 接管页面交互（**水合**过程）。

### 二、核心实现与技术选型

#### 1. 主流 SSR 框架有哪些？它们的区别是什么？

-   **Next.js（React 生态）**：
    -   基于 React，提供零配置 SSR/SSG（静态站点生成）能力；
    -   支持 API 路由、动态路由、图像优化、增量静态再生成（ISR）；
    -   适合大型应用，社区成熟，企业级支持。
-   **Nuxt.js（Vue 生态）**：
    -   基于 Vue，简化 SSR 配置，内置路由、状态管理、中间件；
    -   支持 SSR/SSG/CSR 切换，适合中小型 Vue 项目；
    -   提供自动代码分割、页面预加载等优化能力。
-   **Vue SSR（原生 Vue）**：
    -   需手动配置 Node.js 服务、路由、渲染器，灵活性高；
    -   适合定制化需求，但配置复杂，需处理水合、状态共享等问题。

#### 2. 如何实现 SSR 中的“水合”（Hydration）？

-   **水合的作用**：服务端生成的 HTML 是静态的，客户端 JS 需要将其“激活”，使其具备交互能力（如点击、输入）。
-   **核心步骤**：
    1. 服务端渲染时，给 HTML 元素添加唯一标记（如`data-react-root`）；
    2. 客户端 JS 加载后，通过框架（如 ReactDOM.hydrate、Vue.hydrate）识别标记；
    3. 客户端将静态 HTML 与 JS 状态绑定，替换虚拟 DOM，实现交互。
-   **常见问题**：水合不匹配（服务端与客户端 DOM 结构不一致），需确保前后端渲染逻辑一致。

#### 3. 如何在 SSR 中处理数据请求？

-   **服务端数据请求**：
    -   在组件的`getServerSideProps`（Next.js）或`asyncData`（Nuxt.js）中发起请求；
    -   需在服务端完成数据获取，避免客户端二次请求。
-   **客户端数据请求**：
    -   水合完成后，通过`useEffect`（React）或`mounted`（Vue）发起请求；
    -   需注意：服务端已获取的数据，客户端可复用，避免重复请求。
-   **数据共享**：通过全局状态管理（如 Redux、Pinia）实现服务端与客户端数据同步。

### 三、性能优化与常见问题

#### 1. SSR 的性能瓶颈有哪些？如何优化？

-   **服务端性能瓶颈**：
    -   问题：服务端渲染压力大，高并发下响应慢；
    -   优化：使用缓存（如 Redis 缓存 HTML、数据）、负载均衡、CDN 加速。
-   **首屏加载优化**：
    -   优化：压缩 HTML、JS、CSS，懒加载非关键资源，预加载关键数据。
-   **水合性能优化**：
    -   优化：减少服务端渲染的 DOM 节点数量，避免过度渲染；
    -   避免：服务端生成的 HTML 与客户端虚拟 DOM 结构不一致。

#### 2. 如何解决 SSR 中的“白屏”问题？

-   **原因**：服务端渲染延迟或数据请求失败，导致首屏加载慢。
-   **优化方案**：
    -   服务端缓存 HTML，减少渲染耗时；
    -   预加载关键数据，避免等待数据返回；
    -   使用骨架屏（Skeleton）提升用户体验。

#### 3. SSR 与 SSG（静态站点生成）的区别？

| 对比维度 | SSR                              | SSG                        |
| -------- | -------------------------------- | -------------------------- |
| 生成时机 | 每次请求时生成                   | 构建时生成静态 HTML        |
| 数据依赖 | 动态数据（实时请求）             | 静态数据（构建时获取）     |
| 适用场景 | 动态内容（如电商详情、用户中心） | 静态内容（如博客、官网）   |
| 灵活性   | 高（支持动态路由、实时数据）     | 低（路由固定，数据不可变） |
| 性能     | 中等（需服务端渲染）             | 高（静态文件直接返回）     |

#### 4. 如何在 SSR 中处理路由？

-   **服务端路由**：
    -   基于框架路由配置（如 Next.js 的`pages`目录、Nuxt.js 的`pages`目录）；
    -   服务端根据路由参数匹配对应的页面组件。
-   **客户端路由**：
    -   框架内置路由（如 React Router、Vue Router）；
    -   需注意：服务端路由与客户端路由需保持一致，避免 404 错误。

#### 5. 如何在 SSR 中处理 SEO？

-   **核心优势**：SSR 生成的 HTML 包含完整内容，搜索引擎可直接抓取。
-   **优化方案**：
    -   为每个页面设置`title`、`meta`标签（通过框架配置或组件内设置）；
    -   使用`next-seo`（Next.js）或`vue-meta`（Nuxt.js）管理 SEO 元数据；
    -   避免使用`display: none`隐藏内容，确保搜索引擎可抓取。

### 四、面试常见坑点与注意事项

1. **水合不匹配**：服务端与客户端渲染的 DOM 结构不一致，导致页面异常。需确保前后端渲染逻辑完全一致，避免使用`v-if`/`v-show`等条件渲染在服务端与客户端表现不同。
2. **服务端状态共享**：服务端数据与客户端状态未同步，导致页面数据不一致。需使用全局状态管理工具（如 Redux、Pinia）确保数据共享。
3. **首屏加载速度**：SSR 虽能提升首屏速度，但仍需优化资源加载，避免服务端渲染耗时过长。
4. **兼容性问题**：服务端代码需兼容 Node.js 环境，避免使用浏览器专属 API（如`window`、`document`）。
5. **错误处理**：服务端渲染失败时，需返回友好的错误页面，避免页面空白。

### 总结

SSR 的核心是**服务端生成 HTML，客户端接管交互**，面试中需重点掌握其原理、实现流程、优化方案及常见问题。建议结合具体框架（如 Next.js、Nuxt.js）进行实战，加深对 SSR 的理解。
