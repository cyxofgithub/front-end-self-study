# 4.2 常见崩溃与性能优化

> 识别和处理常见崩溃，掌握 UI 性能、内存和卡顿优化方法。

---

## 一、常见崩溃类型与处理

### 崩溃速查表

| 崩溃类型 | 典型原因 | 修复方式 |
|----------|----------|----------|
| `NullPointerException` | 访问 null 对象的属性/方法 | Kotlin 空安全 `?.` `?:`，避免 `!!` |
| `ClassCastException` | 类型转换错误 | 先 `is` 检查，再转换 |
| `IndexOutOfBoundsException` | 数组/列表越界访问 | 检查 `size`，用 `getOrNull()` |
| `ConcurrentModificationException` | 遍历时修改集合 | 用 `Iterator.remove()` 或 `toMutableList()` 副本 |
| `NetworkOnMainThreadException` | 主线程执行网络操作 | 移到子线程/协程 |
| `CalledFromWrongThreadException` | 子线程更新 UI | 切到主线程 `runOnUiThread` |
| `ActivityNotFoundException` | 跳转目标不存在 | 检查包名/类名，用隐式 Intent 前先 `resolveActivity` |
| `IllegalStateException` | Fragment/View 状态不对 | 检查生命周期，`isAdded()` 判断 |
| `OutOfMemoryError` | 内存不足 | 优化图片加载、检查内存泄漏 |
| `StackOverflowError` | 递归调用过深 | 检查递归终止条件 |

### 崩溃处理最佳实践

```kotlin
// 1. 全局异常捕获
class MyApplication : Application() {
    override fun onCreate() {
        super.onCreate()
        Thread.setDefaultUncaughtExceptionHandler { thread, throwable ->
            Log.e("Crash", "Uncaught exception", throwable)
            // 上报崩溃信息到服务器
            CrashReporter.report(throwable)
            // 重启应用
            restartApp()
        }
    }
}

// 2. 网络请求统一错误处理
suspend fun <T> safeApiCall(call: suspend () -> T): Result<T> {
    return try {
        Result.success(call())
    } catch (e: IOException) {
        Result.failure(NetworkException("网络连接失败", e))
    } catch (e: HttpException) {
        Result.failure(ServerException("服务器错误: ${e.code}", e))
    } catch (e: JsonParseException) {
        Result.failure(ParseException("数据解析错误", e))
    } catch (e: Exception) {
        Result.failure(e)
    }
}

// 3. Fragment 安全操作
fun Fragment.safeShowDialog(dialog: DialogFragment) {
    if (isAdded && !isDetached && !isRemoving) {
        dialog.show(childFragmentManager, "dialog")
    }
}
```

## 二、UI 性能优化

### 过度绘制（Overdraw）

过度绘制 = 同一个像素被绘制了多次。

**检测方法**：
```
开发者选项 → 调试 GPU 过度绘制 → 显示过度绘制区域

颜色含义：
无色     → 没有过度绘制（理想）
蓝色     → 1 次过度绘制（可接受）
绿色     → 2 次过度绘制（需注意）
粉色     → 3 次过度绘制（需优化）
红色     → 4+ 次过度绘制（必须优化）
```

**优化方法**：

```xml
<!-- 不好的做法：多层背景叠加 -->
<LinearLayout android:background="@color/white">
    <LinearLayout android:background="@color/white">
        <TextView android:background="@color/white" />
    </LinearLayout>
</LinearLayout>

<!-- 好的做法：去掉不必要的背景 -->
<LinearLayout android:background="@color/white">
    <LinearLayout>  <!-- 无背景，继承父级 -->
        <TextView />  <!-- 无背景 -->
    </LinearLayout>
</LinearLayout>
```

### 减少布局层级

```xml
<!-- 不好的做法：多层嵌套 -->
<LinearLayout orientation="vertical">
    <LinearLayout orientation="horizontal">
        <TextView />
        <ImageView />
    </LinearLayout>
</LinearLayout>

<!-- 好的做法：用 ConstraintLayout 扁平化 -->
<androidx.constraintlayout.widget.ConstraintLayout>
    <TextView
        app:layout_constraintTop_toTopOf="parent"
        app:layout_constraintStart_toStartOf="parent" />
    <ImageView
        app:layout_constraintTop_toTopOf="parent"
        app:layout_constraintEnd_toEndOf="parent" />
</androidx.constraintlayout.widget.ConstraintLayout>
```

### include 和 ViewStub

```xml
<!-- include — 复用布局 -->
<include layout="@layout/common_title_bar" />

<!-- ViewStub — 懒加载（只在需要时加载） -->
<ViewStub
    android:id="@+id/stub_error"
    android:layout="@layout/error_view"
    android:inflatedId="@+id/error_view" />
```


## 三、内存优化

### 内存泄漏

**常见原因**：长生命周期对象持有短生命周期对象的引用。

```kotlin
// ❌ 内存泄漏：静态变量持有 Activity 引用
object LeakExample {
    var activity: Activity? = null  // Activity 销毁后仍被持有
}

// ✅ 正确：用 WeakReference 或及时清理
object SafeExample {
    private var activityRef: WeakReference<Activity>? = null

    fun setActivity(activity: Activity) {
        activityRef = WeakReference(activity)
    }
}

// ❌ 内存泄漏：匿名内部类持有外部类引用
class MyActivity : Activity() {
    private val runnable = Runnable {
        // 隐式持有 MyActivity 的引用
        updateUI()
    }

    fun start() {
        Handler(Looper.getMainLooper()).postDelayed(runnable, 60000)
    }

    // 必须在 onDestroy 中移除回调
    override fun onDestroy() {
        handler.removeCallbacks(runnable)
        super.onDestroy()
    }
}
```

### 常见泄漏场景

| 场景 | 原因 | 修复 |
|------|------|------|
| 静态变量持有 Activity | Activity 无法被 GC | 用 WeakReference |
| 单例持有 Context | 单例生命周期 > Activity | 用 Application Context |
| 未取消的协程/定时器 | 回调持有 View 引用 | onDestroy 中取消 |
| 未注销的广播/监听器 | 系统持有回调引用 | onDestroy 中注销 |
| 内部类（非静态） | 隐式持有外部类引用 | 改为静态内部类或 Lambda |

### 大图处理

```kotlin
// ❌ 不好的做法：加载原始大图
Glide.with(context)
    .load(imageUrl)
    .into(imageView)  // 可能加载 4000x3000 的原图到只有 200x200 的 ImageView

// ✅ 好的做法：降采样
Glide.with(context)
    .load(imageUrl)
    .override(200, 200)        // 指定目标大小
    .diskCacheStrategy(DiskCacheStrategy.ALL)
    .into(imageView)

// ✅ 使用 BitmapFactory 手动降采样
fun decodeSampledBitmap(path: String, reqWidth: Int, reqHeight: Int): Bitmap {
    // 第一次只读取尺寸
    val options = BitmapFactory.Options().apply { inJustDecodeBounds = true }
    BitmapFactory.decodeFile(path, options)

    // 计算采样率
    options.inSampleSize = calculateInSampleSize(options, reqWidth, reqHeight)
    options.inJustDecodeBounds = false

    return BitmapFactory.decodeFile(path, options)
}

fun calculateInSampleSize(options: BitmapFactory.Options, reqWidth: Int, reqHeight: Int): Int {
    val (height, width) = options.outHeight to options.outWidth
    var inSampleSize = 1
    if (height > reqHeight || width > reqWidth) {
        val halfHeight = height / 2
        val halfWidth = width / 2
        while ((halfHeight / inSampleSize) >= reqHeight &&
               (halfWidth / inSampleSize) >= reqWidth) {
            inSampleSize *= 2
        }
    }
    return inSampleSize
}
```

### Memory Profiler 使用

```
Android Studio → View → Tool Windows → Profiler → Memory

功能：
1. Heap Dump — 查看当前内存中的对象分布
   - 点击 "Capture heap dump"
   - 按类名/包名查找
   - 查看对象的引用链（找出谁持有了不该持有的引用）

2. Allocation Tracking — 追踪一段时间内的对象分配
   - 点击 "Record"
   - 操作应用
   - 点击 "Stop"
   - 查看哪些对象被频繁创建

3. 内存泄漏检测
   - 反复进入退出某个页面
   - 每次 Heap Dump 对比
   - 如果某个对象数量持续增长，说明有泄漏
```

## 四、卡顿优化

### 卡顿原因

1. **主线程做了耗时操作** → 移到子线程
2. **布局层级过深** → 减少嵌套，使用 ConstraintLayout
3. **频繁 GC** → 减少对象创建（尤其在 onDraw 中）
4. **过度绘制** → 减少不必要的背景
5. **图片过大** → 降采样

### 检测卡顿

```bash
# Systrace（系统级追踪）
python systrace.py --time=10 gfx view res

# Perfetto（新一代性能分析）
# https://ui.perfetto.dev/

# 严格模式（开发时检测主线程 IO）
```

```kotlin
// 在 Application 中启用严格模式
fun initStrictMode() {
    if (BuildConfig.DEBUG) {
        StrictMode.setThreadPolicy(
            StrictMode.ThreadPolicy.Builder()
                .detectAll()          // 检测所有主线程违规操作
                .penaltyLog()         // 日志输出
                .build()
        )
        StrictMode.setVmPolicy(
            StrictMode.VmPolicy.Builder()
                .detectAll()
                .penaltyLog()
                .build()
        )
    }
}
```

### 常用优化手段

| 手段 | 说明 |
|------|------|
| 协程替代 Thread | 更轻量，避免阻塞 |
| ConstraintLayout | 减少布局层级 |
| ViewStub | 懒加载不常用的 View |

## 参考答案

### 第 1 题

**操作步骤：**

1. 打开 Android Studio Profiler → Memory
2. 在应用首页点击 **Capture heap dump**，记录基准内存
3. 进入目标页面，操作一会儿
4. 退出目标页面，回到首页
5. 再次点击 **Capture heap dump**
6. 对比两次 dump：如果 Activity/Fragment 对象数量增加且不减少，说明有内存泄漏
7. 点击泄漏对象查看引用链，找到持有引用的根源

### 第 2 题

**操作步骤：**

1. 手机进入 **开发者选项 → 调试 GPU 过度绘制 → 显示过度绘制区域**
2. 屏幕上会显示颜色覆盖：
   - 无色 = 理想（0 次过度绘制）
   - 蓝色 = 可接受（1 次）
   - 绿色 = 需注意（2 次）
   - 粉色 = 需优化（3 次）
   - 红色 = 必须优化（4+ 次）
3. 优化方法：去掉不必要的背景、减少布局层级

### 第 4 题

```kotlin
data class User(val id: String, val name: String, val score: Int)

class UserDiffCallback(
    private val oldList: List<User>,
    private val newList: List<User>
) : DiffUtil.Callback() {

    override fun getOldListSize() = oldList.size
    override fun getNewListSize() = newList.size

    override fun areItemsTheSame(oldPos: Int, newPos: Int): Boolean {
        return oldList[oldPos].id == newList[newPos].id
    }

    override fun areContentsTheSame(oldPos: Int, newPos: Int): Boolean {
        return oldList[oldPos] == newList[newPos]
    }
}

// Adapter 中使用
class UserAdapter : RecyclerView.Adapter<UserViewHolder>() {
    private var items = listOf<User>()

    fun updateData(newItems: List<User>) {
        val diffResult = DiffUtil.calculateDiff(UserDiffCallback(items, newItems))
        items = newItems
        diffResult.dispatchUpdatesTo(this)
    }

    override fun onBindViewHolder(holder: UserViewHolder, position: Int) {
        holder.bind(items[position])
    }

    override fun getItemCount() = items.size
    override fun onCreateViewHolder(parent: ViewGroup, viewType: Int): UserViewHolder {
        val view = LayoutInflater.from(parent.context)
            .inflate(R.layout.item_user, parent, false)
        return UserViewHolder(view)
    }
}
```

## 本章知识点总结

| 知识点 | 要点 |
|--------|------|
| 常见崩溃 | NPE（用空安全）/ 类型转换（先 is 检查）/ 越界（检查 size）/ 主线程网络/子线程 UI |
| 内存泄漏 | 静态变量/单例持有 Activity；未取消协程/回调；未注销监听器 |
| 内存检测 | Memory Profiler Heap Dump；对比进出页面前后的对象数量 |
| 过度绘制 | 开发者选项中检测；去掉不必要背景；减少 View 叠加 |
| StrictMode | 开发期检测主线程 IO 和网络操作；`penaltyLog` 输出到 Logcat |
| DiffUtil | 增量更新列表，只刷新变化的 item；替代 `notifyDataSetChanged` |
| RecyclerView 优化 | DiffUtil + ViewHolder 复用 + `setHasFixedSize` + 避免在 bind 中创建对象 |
| 大图处理 | Glide `.override()` 降采样；`inSampleSize` 手动降采样 |
