# 浏览器扩展面试题（含详解）

> 配套文档：[README.md](./README.md)；配套 demo：`demo-vanilla/`（原生 MV3）、`demo-enterprise/`（企业级工程化）。
> 按难度分三组：基础（必会）→ 进阶（区分度）→ 架构与工程化（中高级岗加分）。

---

## 一、基础题

### 1. 一个浏览器扩展由哪些部分组成？

**答**：四部分 + 一份清单：
- **manifest.json**：配置与权限声明，扩展的"身份证"
- **background（MV3 为 Service Worker）**：事件中心，调浏览器 API、管数据
- **content script**：注入网页的脚本，唯一能直接操作页面 DOM 的角色
- **扩展页面**：popup（点图标弹出）、options（设置页）等普通 HTML 页面

它们运行在**互相隔离**的环境，靠 Chrome 消息机制通信。

### 2. MV2 和 MV3 有什么区别？为什么要推 MV3？

**答**：区别五个关键点：

| 维度 | MV2 | MV3 |
|---|---|---|
| 后台 | 常驻 background page | 事件驱动 Service Worker，空闲即休眠 |
| 远程代码 | 允许 | 禁止，代码必须全部打包 |
| eval | CSP 可放行 | 彻底禁止 |
| 网络拦截 | webRequest 阻塞式 | declarativeNetRequest 声明式，能力受限 |
| 主机权限 | 混在 permissions | 独立 host_permissions |

官方理由：性能（SW 不占常驻内存）、安全（杜绝审核后远程换恶意代码）、隐私（权限最小化）。社区争议：declarativeNetRequest 削弱广告拦截器，被认为是真实动机之一。

### 3. content script 能访问页面的 JS 变量吗？为什么？

**答**：不能。content script 运行在 **isolated world（隔离世界）**：与页面**共享 DOM，但 JS 环境完全独立**——各自有独立全局对象和原型链，页面的 `window.xxx` 在 content script 里是 `undefined`，页面污染 `Array.prototype` 也不影响 content script。这是安全设计，防止恶意页面通过原型链投毒攻击扩展逻辑。

要交换数据只能走公共通道：`window.postMessage` 或 DOM `CustomEvent`。

### 4. content script 里的 localStorage 是扩展的吗？

**答**：不是，是**页面站点**的 localStorage（经典坑）。后果：数据会被站点脚本看到/清掉、按站点隔离（换个网站就读不到）、其他扩展环境访问不到。扩展自己的数据必须用 `chrome.storage`（local/sync/session），它在 content script 中同样可用，且扩展全局共享。

### 5. popup 关闭后里面的数据还在吗？

**答**：不在。popup 每次打开都是**全新加载的页面**，关闭即销毁，JS 状态全丢。持久化要走 `chrome.storage`；想感知数据变化用 `chrome.storage.onChanged` 订阅。

### 6. 扩展的三个环境之间怎么通信？

**答**：

| 方向 | API |
|---|---|
| popup / content → background | `chrome.runtime.sendMessage` |
| background → content | `chrome.tabs.sendMessage(tabId, ...)`（**必须带 tabId**） |
| popup → content | 先 `tabs.query` 拿 tabId 再 `tabs.sendMessage`，或经 background 中转 |
| 长连接 | `chrome.runtime.connect` → `Port.postMessage`，断开触发 `onDisconnect` |
| content ↔ 页面主世界 | `window.postMessage` / `CustomEvent` |

### 7. storage.local / sync / session 的区别？

**答**：
- **local**：~10MB，只存本机，卸载才清 → 大部分数据
- **sync**：总量 100KB、单条 8KB、**写频率有限制**，跟随 Google 账号跨设备同步 → 用户偏好配置；高频写要做节流合并
- **session**：~10MB，只存内存，浏览器关闭即清，但 **SW 休眠不丢** → 会话级临时状态

## 二、进阶题

### 8. MV3 的 Service Worker 生命周期是怎样的？带来了哪些约束？

**答**：SW 是事件驱动的：有事件（消息、闹钟、菜单点击…）时冷启动唤醒，空闲约 30 秒被浏览器回收。三条铁律：

1. **状态不能放全局变量**——重启即丢，持久状态一律 chrome.storage，浏览器托管的状态（如 badge）重启后要恢复
2. **不能用 setInterval 做长延时任务**——休眠后定时器死掉，改用 `chrome.alarms`（最短 30s，响铃会唤醒 SW）
3. **事件监听器必须顶层同步注册**——Chrome 冷启动时只同步执行顶层代码重建监听器清单，放在异步回调里注册会丢事件

"保活 hack"（每 20s 调一个 API）存在但违背设计意图、耗资源、审核可能被拒，不推荐。

### 9. 异步处理消息时为什么要 `return true`？

**答**：`onMessage` 监听器返回后，Chrome 默认认为"不会回包了"，立即关闭消息通道，之后再调 `sendResponse` 就是死信，发送方永久挂起。`return true` 告诉 Chrome"我要异步回包，保持通道"。

```js
chrome.runtime.onMessage.addListener((msg, sender, sendResponse) => {
  chrome.storage.local.get('notes').then(sendResponse);
  return true; // 没有这行，sendResponse 失效
});
```

企业级做法是封装层统一 `return true`（见 demo-enterprise `src/shared/messaging.ts`），业务代码不感知。

### 10. content script 注入失败/没生效，可能的原因？

**答**：
1. **受限页面**：chrome://、Chrome Web Store、PDF 查看器等禁止注入
2. `matches` 没匹配上（协议、域名、路径 pattern 写错）
3. `run_at` 时机问题：`document_start` 时 body 还不存在
4. **改了代码后已打开的页面不会重新注入**——要刷新页面（声明式注入只在页面加载时执行）
5. 页面在扩展安装前就打开了——同理需刷新

### 11. host_permissions 和 permissions 有什么区别？activeTab 是什么？

**答**：
- `permissions` 管 **API 功能**（storage、tabs、alarms…）
- `host_permissions` 管 **能访问哪些站点**（读 DOM、跨域 fetch），MV3 把它从 permissions 拆出来是为了权限粒度更细
- `activeTab`：不给长期权限，语义是"用户点击图标/快捷键**主动激活**的那一刻，临时获得当前标签页访问权"。很多"点一下才干活"的扩展有它就够了，不用声明 `<all_urls>`——审核更快、用户看不到"读取所有网站数据"的警告。这是权限最小化的标准答案。

### 12. MV3 的 CSP 有什么限制？平时怎么踩坑？

**答**：扩展页面强制 `script-src 'self'`：
- **禁止内联脚本**：`<script>` 内联代码、`onclick="..."` 不执行 → 事件必须 `addEventListener`
- **禁止远程脚本**：CDN JS 引不进来，所有代码必须打包进扩展
- **禁止 eval / new Function**：MV2 能用 `unsafe-eval` 放行，MV3 不行 → 依赖 eval 的库（某些模板引擎、旧库）必须替换

易错点：content script **不受页面 CSP 也不受扩展 CSP 约束**；但 content script 往页面插 `<script>` 时，那个脚本跑在页面主世界，受**页面** CSP 约束。

### 13. declarativeNetRequest 是干什么的？为什么广告拦截插件反对 MV3？

**答**：MV3 的网络请求拦截方案：扩展提供**声明式规则清单**（匹配条件 → 动作：block/redirect/改 header），由浏览器原生执行。相比 MV2 的 `webRequest`（扩展 JS 可以阻塞式地检查、修改每个请求），它性能更好、隐私更好（扩展看不到请求内容），但：
- 规则数量有上限（静态规则 3 万条起步、动态规则 5 千）
- **不能编程式决策**——广告拦截器依赖的复杂过滤逻辑（如元素隐藏规则动态生成、按响应内容判断）做不了

所以 uBlock Origin 等认为 MV3 使其核心能力残废，这是 MV3 最大的社区争议。

### 14. 右键菜单（contextMenus）为什么要在 onInstalled 里创建？

**答**：菜单创建后是**持久化**的（浏览器记着，重启还在）。SW 每次冷启动都会执行顶层代码，如果 `contextMenus.create` 写在顶层，第二次启动就报"重复 id"错误。`onInstalled` 只在安装/更新/浏览器升级时触发一次，是所有"一次性初始化"（建菜单、写默认配置）的正确时机。

### 15. content script 如何与页面主世界的 JS 通信？

**答**：两条路：
1. **`window.postMessage`**：双方约定 `type` 协议互相发；接收方要校验 `event.source === window` 和来源协议，防伪造
2. **DOM CustomEvent**：往共享的 DOM 节点上 dispatch/监听自定义事件，数据放 `detail`

如果 content script 需要**执行**主世界代码（如 Hook 页面的 fetch），用 `chrome.scripting.executeScript({ world: 'MAIN' })`，或注入一个在 `web_accessible_resources` 里声明的 `<script>` 标签。

### 16. 网页能检测到用户安装了某个扩展吗？有什么安全含义？

**答**：能，如果扩展把资源声明进了 `web_accessible_resources`：网页尝试 `fetch('chrome-extension://<扩展id>/某资源')` 或加载该 URL 的 `<img>`，成功即说明装了。这带来**用户指纹/隐私泄露**（"装了某密码管理器"本身就是敏感信息），也曾被用于定向攻击。对策：web_accessible_resources 清单最小化；MV3 支持 `use_dynamic_url`（每次会话随机 URL）缓解。

## 三、架构与工程化题

### 17. 你们项目的扩展用的什么技术栈？为什么不用原生写？

**答**（结合 demo-enterprise）：Vite + React + TypeScript + CRXJS。原生裸写的问题：无模块化（几千行全局脚本没法维护）、无类型（消息协议靠字符串约定，重构即灾难）、无 HMR（改一行代码要去 chrome://extensions 点刷新再复现）、无构建优化、UI 复杂后手写 DOM 不可维护。

选型对比：
- **CRXJS**：Vite 插件，保留 Vite 全能力 + manifest 用 TS 定义（`defineManifest` 可做 dev/prod 差异），控制力最强，团队已有 Vite 体系首选
- **Plasmo**：约定优于配置的全家桶，上手最快但黑盒多
- **WXT**：基于 Vite 的现代框架，一套代码多浏览器

### 18. content script 注入的 UI 如何做样式隔离？

**答**：三种方案按隔离强度排序：
1. **类名前缀 + `all: initial`**：零成本但弱，页面 `!important`/内联样式可穿透
2. **Shadow DOM**（主流）：`attachShadow` + 把 React 应用 mount 进 shadow root，CSS 用 `?inline` 字符串注入 shadow 内部——双向隔离，页面选择器进不来、内部样式出不去。注意点：z-index 竞争由宿主节点决定；`?inline` 需要 `vite/client` 类型
3. **iframe**：隔离最强（连 JS 都隔离），但定位/尺寸/通信麻烦，弹层类 UI 才用

demo-enterprise 的 `src/content/index.tsx` 是 Shadow DOM 方案的完整实现。

### 19. 消息通信如何做类型安全和可维护性设计？

**答**：核心是"协议集中定义 + 泛型封装"（demo-enterprise `src/shared/`）：
1. **types.ts**：一张 `MessageMap` 声明全部消息：消息名 → `{ payload, response }`，改协议只动一处
2. **messaging.ts**：`sendToBackground('ADD_NOTE', {...})` 泛型推导——消息名写错、payload 缺字段、返回值类型用错，全部**编译期报错**；封装内统一处理 MV3 的 `return true` 坑和 Promise 化
3. **storage.ts**：schema 化存储（key + 默认值 + 类型集中），`subscribe` 返回取消订阅函数配合 React useEffect 清理

更进一步：真实大厂会用 webext-bridge 解决 content→popup 直发、namespace 隔离，并在封装层统一埋点监控消息失败率。

### 20. 数据流怎么组织？content script 能直接写 storage 吗？

**答**：能写（content script 可以访问 chrome.storage），但企业级做法是 **background 做单一数据中心**：content/popup 只发消息，由 background 统一读写 storage。原因：
- 多标签页并发写同一 key 会互相覆盖（read-modify-write 竞态），收口到 background 可串行化
- 数据变更后由 background 统一更新 badge、发通知等联动逻辑
- 配合 `storage.onChanged` 订阅，各 UI 环境自动获得新数据——形成"background 写 → onChanged 广播 → 各端刷新"的单向数据流

### 21. 扩展如何做 i18n？

**答**：Chrome 原生方案：
- `_locales/<locale>/messages.json` 存文案，manifest 声明 `default_locale`
- manifest 字段用 `__MSG_key__` 占位符；JS 里 `chrome.i18n.getMessage('key')`
- Chrome 按浏览器语言自动选 locale，缺失回退 default_locale
- 支持占位符 `$1$2` 参数化

popup/options 是 React 应用时也可以只用 Chrome 方案管 manifest/background 文案，UI 层用 i18next——但注意保持两套文案一致的成本。demo-enterprise 演示了原生方案。

### 22. 扩展的发布流程？如何灰度？

**答**：
1. 构建打包：`vite build` → 把 `dist/` 打成 zip
2. 上传 Chrome Web Store Developer Dashboard（首次需 $5 开发者注册费）
3. 审核（几小时~几天，权限越多审越慢 → 权限最小化不只是技术问题也是效率问题）
4. 发布：可选**按百分比灰度**（如先 10% 用户），观察崩溃/差评后全量
5. 版本号必须递增（最多 4 段数字）

企业内部分发可走自托管 crx + `update_url`，或 Chrome 企业策略（ExtensionInstallForcelist）强制安装，绕过商店。

### 23. 线上用户反馈"扩展不工作"，你怎么排查？

**答**：分层排查思路：
1. **环境确认**：浏览器及版本、扩展版本、是否在受限页面（chrome:// 等）
2. **SW 状态**：让用户打开 `chrome://extensions` 看 Service Worker 是否报错/崩溃；MV3 最常见的问题是 SW 休眠后状态丢失类 bug
3. **权限**：host_permissions 是否覆盖目标站点；用户是否拒绝过可选权限
4. **复现**：本地装同版本扩展复现；content script 问题检查 matches、页面 CSP、SPA 路由（pushState 不触发重新注入）
5. **预防（工程化回答加分）**：消息层/存储层统一加错误埋点上报；`chrome.runtime.lastError` 全量捕获；关键链路（注入成功、消息成功率）打点监控

### 24. SPA 页面里 content script 有什么坑？

**答**：声明式 content script 只在**页面加载**时注入一次。SPA 用 pushState 切换路由不触发加载，导致：URL 已经变了但扩展还以为在旧页面（按 URL 生效的功能失效）。对策：
- content script 里监听 `popstate` + 劫持 `history.pushState`/`replaceState`（或监听 `navigation` API）
- 用 `MutationObserver` 观察关键 DOM 变化兜底
- background 侧监听 `chrome.tabs.onUpdated`（`status: 'complete'` 且 url 变化）或 `chrome.webNavigation.onHistoryStateUpdated`，再按需 `chrome.scripting.executeScript` 注入

### 25. 开放设计题：设计一个"网页划线笔记"扩展，说说架构。

**答**（这就是本仓库两个 demo 的设计，照此回答）：

**功能拆解**：划词保存、页面高亮回显、笔记列表管理、多端同步。

**架构**：
```
content script  ── 划词监听、<mark> 高亮渲染、Shadow DOM 浮动面板
     │ sendMessage('ADD_NOTE')
     ▼
background SW   ── 单一数据中心：notes 的增删查改全部收口这里
     │              右键菜单/快捷键入口、badge 更新、alarms 定时同步
     ▼
chrome.storage  ── local 存笔记原文（量大）；sync 存配置（跨设备）
     ▲ onChanged 广播
popup / options ── React UI，subscribe storage 自动刷新，不直接写数据
```

**关键设计决策**（每个都能展开追问）：
- 数据收口 background，避免多标签页并发写覆盖（read-modify-write 竞态）
- 高亮回显：存储时用"文本引用（text quote + 前后文锚点）"而非 XPath（页面改版 XPath 易碎）；回显时模糊匹配定位
- 权限最小化：activeTab + scripting 按需注入，不声明 `<all_urls>`
- 样式隔离：Shadow DOM
- 类型安全：消息协议 MessageMap + 泛型封装
- 同步：sync 配额小（100KB），笔记正文走 local，只把"同步开关/颜色配置"放 sync；如需真正的云端笔记同步，接自己后端（background 里 fetch + OAuth `chrome.identity`）
- 性能：content script 注入尽量轻（按需注入），大列表虚拟滚动，storage 写入节流
