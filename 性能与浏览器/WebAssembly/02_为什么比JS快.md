# 为什么 WASM / Java / C++ 比 JS 执行效率高

> 核心结论先行：**JS 的慢不是"解释执行"这一个点慢，而是从下载 → 解析 → 编译 → 执行 → 内存管理整条链路上，每个环节都在为"动态类型"和"灵活性"付税**。编译型语言（C++）、托管编译语言（Java）和 WASM 分别在链路的哪些环节省掉了这些税，决定了它们各自快多少。

---

## 零、前置概念：先搞懂这些词

> 阅读本文前需要理解的术语。如果已熟悉 V8 工作原理可直接跳到第一节。

### 0.1 两种翻译策略：解释 vs 编译

CPU 只认识**机器码**（0/1 指令），而我们写的 JS 只是**文本**，中间必须"翻译"。用一个类比：**读一本外语小说**。

| 策略 | 类比 | 特点 |
|---|---|---|
| **解释执行**（Interpreter） | **同声传译**：读一句、翻一句、执行一句 | 立刻就能开始，但每句现翻，慢 |
| **编译执行**（Compiler） | **笔译**：先整篇翻译成母语，之后反复读 | 翻译耗时，但翻译完读起来飞快 |

翻译的中间产物：

- **AST（抽象语法树）**：把文本代码解析成结构化的树，让机器"理解"代码结构（哪些是函数、哪些是表达式）。
- **字节码（Bytecode）**：介于源码和机器码之间的中间格式——比文本紧凑，比机器码通用（不绑定具体 CPU）。Java 的 `.class`、JS 引擎内部都用它。

### 0.2 V8 里的四个角色

V8 是 Chrome / Node.js 的 JS 引擎，它把"解释"和"编译"组合使用：

| 名词 | 是什么 | 类比 |
|---|---|---|
| **Parser** | 把 JS 文本读进去、检查语法、生成 AST | 把小说文字读进去、理解句子结构 |
| **Ignition** | V8 的**解释器**：AST → 字节码，逐条执行 | 同声传译 |
| **Profiler** | **监视器**：统计哪些函数被反复执行（这种函数叫"**热点**"，Hotspot） | 观察你哪几章翻来覆去地读 |
| **TurboFan** | V8 的**优化编译器**：把热点函数的字节码编译成机器码 | 把反复读的章节认真笔译出来 |

### 0.3 由它们组合出的三个"现象"

- **JIT（Just-In-Time，即时编译）**：就是上面这套组合策略本身——**先解释着跑，发现热点再编译成机器码**。"Just in time" 意为"用到（热点）了才编译"，不为只跑一次的代码浪费编译时间。
- **JIT 预热（warmup）**：从"代码开始跑"到"热点被编译成机器码"之间的**慢速期**。就像小说开头只能听同传，等笔译完成才读得快。页面刚加载的几百毫秒 JS 都在慢速档，就是这个原因。
- **Deopt（去优化）**：编译器**猜错了**的后果。TurboFan 编译时会基于运行现状做假设：

```js
function add(a, b) { return a + b; }

add(1, 2); // 重复调用几万次……
// Profiler 发现 add 是热点 → TurboFan 假设 a、b 永远是 number
// → 编译出"一条加法指令"的机器码，飞快

add("1", "2"); // 突然传了字符串！假设被打破
// → 已编译的机器码整个作废，回退解释器重新收集热点 ← 这就是 deopt
```

Java / C++ / WASM 没有这个问题，正因为类型写在源码里（`int a`），编译时就是确定的——**没有"猜"这个环节，自然也不会猜错**。

### 0.4 另外三个贯穿本文的词

- **AOT（Ahead-of-Time，预先编译）**：与 JIT 相对，程序**运行之前**就完整编译成机器码（C/C++/Rust 的模式）。运行时零编译成本。
- **GC（垃圾回收）**：JS/Java 自动回收不再使用的内存，开发者不用手动释放。
- **STW（Stop-The-World）**：GC 工作时要**暂停**业务代码执行（像地铁临时停车），对象越多停顿越久，对游戏帧循环、音视频处理这种实时场景是硬伤。

## 一、JS 的完整执行链路（以 V8 为例）

```mermaid
flowchart LR
  A["① 下载 JS 文本"] --> B["② Parser 解析为 AST"]
  B --> C["③ Ignition 生成字节码<br/>（解释执行，慢）"]
  C --> D["④ Profiler 收集热点"]
  D --> E["⑤ TurboFan JIT 编译为机器码<br/>（快，但编译本身耗时）"]
  E --> F["⑥ 类型变了？去优化 Deopt<br/>回退字节码重来"]
  F --> D
```

### 链路上的四个瓶颈

1. **解析成本高**
   JS 是文本格式，引擎要做词法分析 → 语法分析生成 AST → 再生成字节码。代码体积越大，解析越慢。这是纯"启动税"，和业务逻辑无关。

2. **先解释、后编译（JIT 预热）**
   V8 不会一上来就编译成机器码——编译本身很耗时，对只跑一次的代码不划算。所以先用 Ignition 解释器跑（慢），Profiler 发现某段代码是热点后，才交给 TurboFan 编译成机器码（快）。这个"预热"过程可能要数百毫秒，且**冷代码永远跑在慢速档**。

3. **动态类型的运行时开销**
   JS 变量没有类型，引擎只能在运行时做两件事：
   - **类型检查 + 隐式转换**：`a + b` 在 CPU 眼里不是一条加法指令——引擎要先查 a、b 是 number 还是 string 还是对象，决定走哪条分支，甚至触发隐式转换。
   - **隐藏类（Hidden Class）+ 内联缓存（Inline Cache）**：访问 `obj.x` 时，V8 靠隐藏类把"属性查找"优化成"固定偏移量读取"，但这个优化只在对象结构稳定时成立。

4. **去优化（Deopt）与 GC 停顿**
   - JIT 编译时**假设**了类型（比如 `a` 一直是 number）。一旦运行时类型变了，已编译的机器码整体作废，回退字节码重新收集热点——性能断崖式下跌，且可能反复发生。
   - V8 垃圾回收需要暂停 JS 执行（Stop-The-World），对象越多、停顿越久，对实时场景（音视频、游戏帧循环）是硬伤。

## 二、C++ 为什么快：在写代码时就付完所有"税"

C++ 是 **AOT（Ahead-of-Time）编译**：程序运行**之前**，编译器已经把源码完整翻译成目标平台的机器码。运行时零编译成本。

| JS 的运行时开销 | C++ 为什么能省掉 |
|---|---|
| 解析文本 → AST → 字节码 | 可执行文件就是机器码，CPU 直接跑 |
| 运行时类型检查、隐式转换 | **静态类型**：`int a` 就是 4 字节整数，`a + b` 编译期就确定是一条 `add` 指令 |
| JIT 预热 | 无预热，第一条指令就是全速 |
| 去优化 | 类型编译期锁定，不存在"类型变了"这件事 |
| GC 停顿 | 手动内存管理（或 RAII 智能指针），析构时机确定，无后台 GC 线程 |

此外还有编译期优化的红利：编译器有**充足的时间**做内联展开、常量折叠、循环展开、寄存器分配、死代码消除——JIT 必须在毫秒内完成编译，AOT 编译器可以花几分钟慢慢优化。

> 一句话：**C++ 把类型确定、内存布局、编译优化全部提前到编译期完成，运行时只剩下纯粹的计算。**

## 三、Java 为什么比 JS 快：同样是 JIT，但"税"少得多

Java 的运行模型和 JS 其实很像（字节码 + 解释 + JIT 热点编译 + GC），但它仍然明显快于 JS，差距来自**静态类型**这一个根本区别：

1. **JIT 编译更便宜、更稳定**
   Java 变量类型在源码里写死，JVM 的 JIT 不需要"猜测"类型，编译出的机器码几乎不需要为类型变化留后门。Deopt 存在但极少触发（主要因为多态和反射），不像 JS 是家常便饭。

2. **对象内存布局确定**
   Java 对象的字段类型和布局编译期可知，字段访问就是固定偏移量的内存读取，不需要 JS 那套隐藏类 + 内联缓存的投机机制。

3. **值类型与原生数组**
   `int[]` 是一块连续内存；JS 的 `Array` 本质上是字典/对象的混合体，可能存任何类型，访问和遍历开销大得多。

4. **GC 更成熟**（相对优势）
   JVM 分代 GC（G1/ZGC/Shenandoah）停顿可压到毫秒甚至亚毫秒级，且 Java 对象分配模式相对规整，GC 效率高于 JS 引擎面对的高度动态对象图。

> 一句话：**Java 和 JS 一样是"边跑边编译"，但静态类型让它的 JIT 几乎不用猜、不用回退，所以预热后稳定在高档位。**

## 四、WASM 为什么快：在浏览器里复刻 C++ 的链路

WASM 可以理解为：**把 C++/Rust 的 AOT 成果打包成一种浏览器认识的二进制格式**，让 Web 也能享受"静态类型 + 提前编译"的红利。

```mermaid
flowchart LR
  A["① 下载 .wasm 二进制"] --> B["② 解码二进制<br/>（比解析文本快 10-20 倍）"]
  B --> C["③ 一次性编译为机器码<br/>（无解释执行阶段）"]
  C --> D["④ 稳定执行<br/>（无去优化、无 GC 停顿）"]
```

对应 JS 的每个瓶颈：

| 环节 | JS | WASM | 差距原因 |
|---|---|---|---|
| **下载** | 文本格式，体积大 | 二进制格式，同等逻辑体积小 30-50% | 二进制天然紧凑 |
| **解析** | 词法分析 → AST → 字节码 | 二进制解码，结构已确定；支持**流式编译**（边下载边编译） | 省掉整个 Parser 阶段 |
| **编译** | 先解释，热点才 JIT，预热慢 | 一次性编译为机器码，无预热 | 省掉"解释 → 收集热点 → JIT"的渐进过程 |
| **执行** | 动态类型运行时检查；可能 deopt | **只有 4 种类型**（`i32/i64/f32/f64`），每条指令都是确定的机器操作 | 无类型判断开销，无去优化 |
| **内存** | GC 自动回收，有 STW 停顿 | **线性内存**手动管理，一块连续的 `ArrayBuffer` | 无 GC 暂停，适合实时/高频计算 |

### WASM 的设计如何支撑"快"

- **栈式虚拟机模型**：指令通过入栈/出栈工作（如 `i32.add` 弹出两个数相加压回），编译到真实机器码时映射直接、无歧义。
- **极简类型系统**：没有字符串、对象、原型链，只有数值。一次字符比较就是一条 `i32.eq`；JS 做同样的事要先查类型、可能隐式转换，**实际执行的指令数是 WASM 的 3-5 倍**。
- **线性内存**：单一连续内存空间，与 JS 通过 `ArrayBuffer` 共享。内存布局由编译器静态规划，访问就是基址 + 偏移。
- **性能可预测**：没有 JIT 预热曲线和 deopt 悬崖，第一帧和第一万帧一样快——这对音视频编解码、游戏物理引擎比"峰值性能"更重要。

> 一句话：**WASM 把 C++/Rust 在编译期确定的类型、内存布局、机器指令，以二进制形式原封不动搬进浏览器，JS 引擎只做解码和翻译，不做猜测。**

## 五、横向对比总表

| 维度 | C++ | Java | WASM | JS |
|---|---|---|---|---|
| 编译时机 | AOT（运行前） | JIT（运行时热点） | 加载时一次性编译 | 解释 + JIT |
| 类型系统 | 静态 | 静态 | 静态（仅 4 种数值） | 动态 |
| 预热 | 无 | 有，但稳定后极少回退 | 无 | 有，且可能反复 deopt |
| 内存管理 | 手动 / RAII | GC（分代，停顿可控） | 线性内存手动管理 | GC（STW 停顿） |
| 运行时类型检查 | 无 | 极少 | 无 | 每条操作都可能要 |
| 运行环境 | 原生 | JVM | 浏览器 / Node / 边缘 | 浏览器 / Node |
| 相对速度（计算密集） | ★★★★★ | ★★★★ | ★★★★（接近原生） | ★★（JIT 后 ★★★） |

## 六、什么时候 JS 并不输

避免形成"JS 一定慢"的误区，面试中主动提这些是加分项：

1. **热点代码 JIT 后差距缩小**：V8 的 TurboFan 非常强大，长时间运行的热点数值计算，JIT 后的 JS 可以接近 WASM 的 70-80%。WASM 的优势主要在**启动速度**和**性能稳定可预测**。
2. **瓶颈不在 JS 时，换 WASM 没用**：DOM 操作、网络 I/O、布局渲染才是瓶颈的场景（绝大多数普通 Web 页面），JS 执行只占很小比例。
3. **JS ↔ WASM 有边界开销**：两者互相调用时要跨边界拷贝/转换数据（尤其是字符串和复杂对象）。频繁小粒度调用 WASM 可能比纯 JS 更慢——WASM 适合**大块、独立、计算密集**的任务。
4. **Java 的 JIT 在长稳态下可反超 AOT**：JVM 能基于运行时真实 profiling 做激进内联（C++ 编译期看不到运行时数据），所以长跑服务端程序 Java 不一定输 C++。

## 七、面试速记

> **Q: 为什么 WASM / Java / C++ 比 JS 快？**
>
> JS 的慢是"动态类型"在全链路上的税：
> - 解析阶段：文本要过完整 Parser；WASM 二进制解码快 10-20 倍
> - 编译阶段：先解释后 JIT，有预热；C++ AOT 零预热，WASM 加载时一次编译完
> - 执行阶段：每条操作要运行时查类型，JIT 还可能 deopt 回退；静态类型语言每条指令都是确定的机器操作，一次比较一条指令 vs JS 的 3-5 倍
> - 内存阶段：GC 有 STW 停顿；C++/WASM 手动内存无停顿，Java GC 停顿可控
>
> 本质是**"决策放在编译期还是运行时"**——编译期能确定的越多，运行时要做的越少，就越快。
