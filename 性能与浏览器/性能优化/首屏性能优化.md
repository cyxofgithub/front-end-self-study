## 讲讲首屏性能优化

首屏性能（LCP/FCP）直接影响用户留存和转化率。以下从核心原因和优化方案两个维度展开。

### 一、前端首屏加载慢的核心原因

#### 1. 网络链路长

- **DNS 解析**：域名首次解析需要 20–120ms
- **TCP 连接**：三次握手，HTTPS 还需 TLS 协商，累计 1–3 个 RTT
- **服务器处理**：SSR 场景下服务端渲染耗时直接拖慢 TTFB
- **带宽限制**：弱网环境下大资源下载慢

> **示例**：一个未优化的 SPA 应用，典型网络耗时链路：
>
> ```
> DNS 解析(50ms) → TCP 连接(80ms) → TLS 握手(150ms) → 请求 HTML(200ms)
> → 解析 HTML → 请求 JS/CSS(500ms+) → 执行 JS → 请求 API 数据(300ms) → 渲染首屏
> ```
>
> 在 4G 弱网下，用户看到有意义内容之前累计耗时 3s+。

#### 2. 关键渲染路径被阻塞

- **CSS 阻塞渲染**：浏览器必须等待所有外部 CSS 加载完毕才能开始渲染
- **JS 阻塞解析**：`<script>` 标签默认中断 HTML 解析，等待 JS 下载并执行
- **未内联关键 CSS**：首屏需要的样式混在全量 CSS 中，导致渲染延迟
- **字体/图片阻塞**：未设置 `font-display` 导致文字隐藏；首屏大图未优先加载

#### 3. 资源体积过大

- **JS Bundle 过大**：未做代码分割，首屏加载了整个应用的所有 JS
- **未压缩/未最小化**：代码中的注释、空格、长变量名增加体积
- **图片未优化**：使用了未压缩的高清大图，或不合适的格式（PNG 而非 WebP/AVIF）
- **第三方库冗余**：lodash 全量引入、Moment.js 带全量 locale 等

#### 4. 渲染策略不当

- **纯 CSR**：白屏时间长，JS 加载并执行完毕后才能渲染
- **未使用骨架屏/Loading**：白屏期间无任何反馈，用户感知更慢
- **DOM 复杂度过高**：首屏大量节点，Layout/Paint 耗时长

### 二、通用首屏优化方案

#### 1. 网络链路优化

| 手段             | 说明                                                 |
| ---------------- | ---------------------------------------------------- |
| CDN 加速         | 静态资源就近访问，减少 RTT                           |
| HTTP/2 或 HTTP/3 | 多路复用，减少连接数开销                             |
| DNS 预解析       | `<link rel="dns-prefetch" href="//api.example.com">` |
| 预连接           | `<link rel="preconnect" href="//cdn.example.com">`   |
| 升级 TLS 1.3     | 减少握手 RTT（2-RTT → 1-RTT）                        |

#### 2. 资源加载策略

- **代码分割（Code Splitting）**：
    - 路由级分割：`React.lazy()` / `defineAsyncComponent()`
    - 组件级分割：首屏非必要组件动态导入
- **关键资源预加载**：
    ```html
    <link rel="preload" href="/fonts/main.woff2" as="font" crossorigin />
    <link rel="preload" href="/css/critical.css" as="style" />
    ```
- **非关键资源延迟加载**：
    ```html
    <script defer src="/app.js"></script>
    <!-- HTML 解析完毕后执行 -->
    <link rel="prefetch" href="/next-page.js" />
    <!-- 空闲时预取下一页 -->
    ```
- **图片懒加载**：
    ```html
    <img loading="lazy" src="photo.jpg" alt="首屏关键图片不使用 lazy" />
    ```

#### 3. 缩小关键资源体积

- **Tree Shaking**：确保 ESM 语法，`package.json` 设置 `"sideEffects": false`
- **SplitChunks**：`react`/`vue` 等框架单独打包，利用浏览器长期缓存
- **按需引入**：`import { debounce } from 'lodash-es'` 而非 `import _ from 'lodash'`
- **Gzip/Brotli**：Nginx 开启 `gzip on` 或 `brotli on`，通常减少 70%+ 的体积
- **CSS 去冗余**：PurgeCSS 移除未使用样式
- **图片优化**：WebP/AVIF 格式 + 响应式图片（`srcset` + `sizes`）+ 压缩

#### 4. 渲染路径优化

- **关键 CSS 内联**：提取首屏需要的样式，直接内嵌到 `<head>` 中，其余 CSS 延迟加载
- **SSR / SSG / ISR**：

    | 方案                | 适用场景                               |
    | ------------------- | -------------------------------------- |
    | SSR（服务端渲染）   | SEO 强需求、内容动态（电商、资讯）     |
    | SSG（静态生成）     | 内容不常变化（博客、文档站）           |
    | ISR（增量静态再生） | 内容偶尔更新，兼顾静态速度和内容新鲜度 |

- **骨架屏**：给用户即时的视觉反馈，改善感知性能
- **避免 JS 阻塞渲染**：
    ```html
    <script async src="/analytics.js"></script>
    <!-- 非关键脚本，下载完即执行 -->
    <script defer src="/main.js"></script>
    <!-- 需要 DOM 但不阻塞解析 -->
    ```

#### 5. 构建与缓存层面

- **HTTP 缓存策略**：
    ```
    HTML:        Cache-Control: no-cache          （每次都验证，保证及时更新）
    JS/CSS(hash): Cache-Control: max-age=31536000 （文件名带 hash，一年强缓存）
    图片:         Cache-Control: max-age=86400     （一天）
    ```
- **Service Worker**：Workbox 方案，对首屏关键资源做预缓存，支持离线/弱网
- **构建工具升级**：Vite/Rspack 基于 ESM 原生支持，HMR 快，生产构建产物更优
- **SSR + Streaming**：React 18+ 的 `renderToPipeableStream`，边渲染边输出 HTML

#### 6. 如何量化首屏性能

##### 6.1 量化工具

| 工具 | 数据来源 | 适用场景 |
|---|---|---|
| **Lighthouse** | 模拟（Simulated），可配置网络/CPU 节流 | 开发阶段定位问题，给出优化建议 |
| **Chrome DevTools Performance** | 实测（现场录制），真实设备数据 | 深入分析火焰图、网络瀑布、帧时间线 |
| **Web Vitals 库（web-vitals）** | RUM（Real User Monitoring），真实用户数据 | 生产环境采集，接入 Analytics |
| **Chrome UX Report（CrUX）** | 真实 Chrome 用户的匿名数据 | 竞品分析、大盘数据参考 |
| **PageSpeed Insights** | Lighthouse + CrUX 双数据 | 既有实验室数据也有现场数据 |

> **示例 - 用 web-vitals 库上报 RUM 数据**：
>
> ```js
> import { onLCP, onFCP, onTTFB, onINP, onCLS } from 'web-vitals';
>
> // 采集并上报到自建或第三方分析平台
> onLCP((metric) => {
>   analytics.send({
>     name: 'LCP',
>     value: metric.value,
>     rating: metric.rating, // 'good' | 'needs-improvement' | 'poor'
>     entries: metric.entries, // PerformanceEntry 数组，可定位 LCP 元素
>   });
> });
> onFCP((metric) => analytics.send({ name: 'FCP', value: metric.value }));
> onTTFB((metric) => analytics.send({ name: 'TTFB', value: metric.value }));
> onINP((metric) => analytics.send({ name: 'INP', value: metric.value }));
> onCLS((metric) => analytics.send({ name: 'CLS', value: metric.value }));
> ```
>
> `metric.entries[0].element` 可以直接拿到 LCP 元素，用来按页面/组件分类统计，快速定位是哪个元素拖慢了 LCP。

##### 6.2 核心性能指标详解

**以用户为中心的性能模型**——按加载阶段划分：

```
请求页面 ──→ 第一个像素 ──→ 第一块内容 ──→ 主要内容可见 ──→ 可交互
           FP                FCP               LCP               TTI
```

| 指标 | 全称 | 含义 | 计算公式 | 合格线 | 数据采集方式 |
|---|---|---|---|---|---|
| **FP** | First Paint | 浏览器首次在屏幕上渲染任何视觉内容（背景色、border 等），即页面不再是空白 | `performance.getEntriesByType('paint').find(e => e.name === 'first-paint').startTime` | —（非 Core Web Vitals） | Paint Timing API |
| **FCP** | First Contentful Paint | 浏览器首次渲染任何 DOM 内容（文字、图片、SVG、非空白 canvas） | `performance.getEntriesByType('paint').find(e => e.name === 'first-contentful-paint').startTime` | < 1.8s | Paint Timing API |
| **LCP** | Largest Contentful Paint | 视口内**最大可见内容元素**完成渲染的时间。候选元素包括 `<img>`、`<video>` 封面、带背景图的元素、包含文本的块级元素 | 浏览器持续监测，取视口内最大元素的渲染时间，直到用户交互（滚动、点击、键盘输入）或页面完全加载 | < 2.5s | Largest Contentful Paint API |
| **TTI** | Time to Interactive | 页面**完全可交互**——长任务（>50ms）结束、网络空闲至少 5s。此时用户可流畅操作 | 首个 5s 无长任务窗口的结束时间 | < 5s | Lighthouse 计算 |
| **TTFB** | Time to First Byte | 从请求发出到收到第一个字节的时间，反映服务器和网络响应速度 | `performance.timing.responseStart - performance.timing.requestStart` | < 800ms | Navigation Timing API |
| **CLS** | Cumulative Layout Shift | 页面生命周期内所有意外布局偏移的累计分数，衡量视觉稳定性 | `impact fraction × distance fraction` 的累计和 | < 0.1 | Layout Instability API |
| **INP** | Interaction to Next Paint | 从用户交互（点击、输入、按键）到下一帧绘制的延迟，2024年3月起取代 FID 成为 Core Web Vitals | 所有交互的延迟中，取接近最差的那个值（通常是 98 百分位） | < 200ms | Event Timing API |

> **示例 - LCP 的判定过程**：
>
> 假设页面加载过程中：
> 1. 0.8s —— 一段文字的 `<p>` 渲染，占据视口 30% → LCP 候选：0.8s
> 2. 1.2s —— 一张横幅 `<img>` 渲染，占据视口 60%（比上一个更大）→ LCP 候选更新为 1.2s
> 3. 2.0s —— 英雄图 `<img>` 渲染，占据视口 80%（大于横幅）→ LCP 候选更新为 2.0s
> 4. 2.5s —— 用户滚动页面，LCP 停止观测
>
> 最终 LCP = 2.0s（英雄图），rating = "good"（< 2.5s）。

> **示例 - CLS 的计算**：
>
> 某广告横幅在正文渲染后被注入，向下推移了 400px 的内容：
>
> ```
> impact fraction  = 被影响的视口高度 / 总视口高度 = 400 / 800 = 0.5
> distance fraction = 元素移动距离 / 视口高度 = 200 / 800 = 0.25
> layout shift score = 0.5 × 0.25 = 0.125
> ```
>
> 单次偏移 0.125 就超过了 0.1 的合格线，这就是为什么广告/动态注入内容需要预留占位空间。

#### 7. 如何针对性优化 LCP

LCP 是 Core Web Vitals 中最常不合格的指标，因为它的成因最复杂。将 LCP 拆解为 **4 个子阶段**，逐个击破：

```
LCP = TTFB + 资源加载延迟 + 资源加载时间 + 元素渲染延迟
```

| 子阶段 | 含义 | 典型耗时占比 | 关键瓶颈 |
|---|---|---|---|
| **TTFB** | 从请求到收到首字节 | ~40% | 服务端响应、重定向、网络延迟 |
| **资源加载延迟** | 浏览器发现资源到开始下载 | ~10% | 资源在 HTML 中的位置、优先级 |
| **资源加载时间** | 下载资源本身 | ~40% | 资源体积、CDN、网络 |
| **元素渲染延迟** | 资源下载完到渲染到屏幕 | ~10% | JS 阻塞、CSS 阻塞、客户端渲染 |

##### 7.1 优化 TTFB

**问题诊断**：在 Chrome DevTools Performance 面板中查看 `requestStart → responseStart` 的耗时。

| 手段 | 说明 | 示例 |
|---|---|---|
| **减少重定向** | 每个 301/302 重定向增加 1 个 RTT | 避免 `http://` → `https://` → `www.` 的多次跳转链 |
| **服务端缓存** | 对热门内容做页面级缓存（CDN 边缘缓存、Redis） | Nginx 反向代理缓存：`proxy_cache_path` + `proxy_cache_valid` |
| **SSG 预渲染** | 构建时生成静态 HTML，直接返回，没有服务端处理耗时 | Next.js `getStaticProps`、Nuxt `nuxt generate` |
| **CDN 回源优化** | 确保 LCP 资源的 CDN 节点离用户足够近 | CDN 预热热点内容，减少回源率 |
| **服务端计算优化** | 慢接口异步化、数据库查询加索引、SSR 首屏数据只请求必要字段 | 避免 SSR 时 `await` 全部接口再返回 HTML，使用 Streaming SSR |

> **示例 - Streaming SSR（React 18+）**：
>
> ```jsx
> // 传统 SSR：等所有数据就绪才返回 HTML
> const html = renderToString(<App data={await fetchAll()} />);
>
> // 流式 SSR：先发送 Shell，数据就绪后流式注入
> const { pipe } = renderToPipeableStream(<App />, {
>   onShellReady() { pipe(response); } // Shell 就绪立即发送
> });
> ```

##### 7.2 优化资源加载延迟

**问题诊断**：Lighthouse 会提示 "Reduce initial server response time" 或 "Preload key requests"。Chrome DevTools Network 面板查看 LCP 资源的时间线，关注从 HTML 解析到资源下载开始之间的间隙。

| 手段 | 说明 | 示例 |
|---|---|---|
| **`<link rel="preload">`** | 提高 LCP 资源的优先级，让浏览器提前下载 | `<link rel="preload" as="image" href="hero.webp" />` |
| **从 HTML 直接引用** | 避免 JS 动态创建 LCP 元素——浏览器预加载扫描器只能解析 HTML 中的静态引用 | 英雄图用 `<img>` 而非 `JS new Image()` |
| **移除懒加载** | LCP 资源不能使用 `loading="lazy"`，否则浏览器会延迟下载（所有浏览器都这样） | 确保 LCP 图片没有 `loading="lazy"` 属性 |
| **`fetchpriority="high"`** | 显式提升关键资源的网络优先级 | `<img src="hero.webp" fetchpriority="high" />` |

> **示例 - 对比**：
>
> ```html
> <!-- ❌ 差：JS 动态创建图片，预加载扫描器看不到 -->
> <div id="hero"></div>
> <script>
>   document.getElementById('hero').innerHTML = '<img src="hero.webp" />';
> </script>
>
> <!-- ✅ 好：静态 HTML，预加载扫描器立即发现并下载 -->
> <img src="hero.webp" fetchpriority="high" />
> ```

##### 7.3 优化资源加载时间

**问题诊断**：Network 面板查看 LCP 资源的下载耗时（Content Download 阶段）。

| 手段 | 说明 | 示例 |
|---|---|---|
| **图片格式升级** | AVIF 比 WebP 再小 30%，比 JPEG 小 50%+ | `<picture><source srcset="hero.avif" type="image/avif" /><img src="hero.jpg" /></picture>` |
| **响应式图片** | 移动端不需要桌面端大图 | `<img srcset="hero-640.webp 640w, hero-1280.webp 1280w" sizes="(max-width: 640px) 100vw, 1280px" />` |
| **CDN + 压缩** | CDN 实时压缩/转换格式 | 开启 CDN 的 Brotli 压缩、自动 WebP/AVIF 转换 |
| **关键 CSS 内联** | 避免 LCP 渲染等外部 CSS 加载 | 提取首屏关键样式内联到 `<head>`，其余异步加载 |
| **去除非关键代码** | 移除阻塞首屏的未使用 JS/CSS | PurgeCSS、动态 import、条件加载 |

> **示例 - 关键 CSS 内联方案**：
>
> ```js
> // webpack 配置使用 critters-webpack-plugin 或 critical
> // 或手动提取：
> const criticalCSS = `
>   /* 首屏必需的样式：header、hero、above-the-fold 布局 */
>   .header { ... }
>   .hero { display: flex; ... }
>   .hero__image { width: 100%; max-width: 1280px; }
> `.replace(/\s+/g, ' ');
> ```

##### 7.4 优化元素渲染延迟

**问题诊断**：Performance 面板中查看 LCP 元素绘制时间与该资源下载完成时间的差值。

| 手段 | 说明 | 示例 |
|---|---|---|
| **淘汰阻塞渲染的 JS** | 同步 `<script>` 会阻断 HTML 解析，推迟 LCP 元素渲染 | 加 `async`/`defer`，或者移到 `<body>` 末尾 |
| **TBT/长任务优化** | 主线程忙于执行长任务时无法渲染 → 拆分长任务 | `scheduler.postTask()`、`requestIdleCallback()`、Web Worker |
| **避免 layout thrashing** | 强制同步布局在 JS 中反复触发 reflow | 读写分离，批量 DOM 操作使用 `documentFragment` 或框架的批量更新 |
| **非首屏组件延迟渲染** | 减少首帧的 DOM 节点和样式计算量 | `content-visibility: auto` 对非首屏区域跳过渲染 |

> **示例 - 长任务拆分**：
>
> ```js
> // ❌ 长任务阻塞渲染 200ms
> function processItems(items) {
>   items.forEach(item => heavyTransform(item)); // 单次长任务
> }
>
> // ✅ 拆分长任务 + 让出主线程
> async function processItems(items) {
>   for (const item of items) {
>     heavyTransform(item);
>     if (items.indexOf(item) % 5 === 0) {
>       await scheduler.yield(); // 或 await new Promise(r => setTimeout(r, 0))
>     }
>   }
> }
> ```

##### 7.5 LCP 优化检查清单

按优先级排序：

1. **LCP 元素是否是 `<img>` / 背景图？** → 使用 `preload` + `fetchpriority="high"` + 确保没有 `loading="lazy"` + AVIF/WebP 格式
2. **TTFB 是否 > 800ms？** → 检查服务端处理时长、CDN 回源率、是否有不必要的重定向
3. **LCP 元素是否由 JS 动态创建？** → 改为 HTML 静态引用，让预加载扫描器发现
4. **LCP 资源下载前是否有长空白？** → 检查是否有 CSS/JS 阻塞 HTML 解析
5. **是否有第三方脚本在 `<head>` 中同步加载？** → 改为 `async`/`defer` 或延迟加载
6. **首屏是否渲染了太多元素？** → 虚拟滚动 / `content-visibility: auto` / 分页

---

### 总结

首屏优化遵循一个核心原则：**让关键路径上的资源尽可能少、尽可能小、尽可能快**。

- **少**：只加载首屏所需的 HTML/CSS/JS，其余延迟或按需加载
- **小**：压缩、Tree Shaking、按需引入、现代图片格式
- **快**：CDN、缓存、预加载、SSR/SSG、HTTP/2

```
网络层（CDN / HTTP2 / 预连接）
      ↓
资源层（代码分割 / 压缩 / 缓存）
      ↓
渲染层（SSR / 骨架屏 / 关键CSS内联）
      ↓
    → → → 首屏快速呈现
```

每个环节缺一不可，通常需要组合使用才能达到理想的 LCP 时间。
