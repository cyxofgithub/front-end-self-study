# OOP 代码风格规则

## 适用范围

- 适用于全仓库内所有代码示例、实现建议与重构方案。
- 目标是优先使用面向对象组织方式，但不强制排斥函数式写法。

## 核心原则

- 业务逻辑优先进行对象建模：实体（Entity）、服务（Service）、策略（Strategy）、仓储（Repository）等。
- 尽量将状态与行为封装在类或对象中，减少松散的全局函数与跨模块可变状态。
- 通过接口或抽象类定义边界，优先组合（composition）而非深层继承（inheritance）。
- 面向扩展设计公开 API：新增能力优先通过新类/策略扩展，而非频繁修改旧实现。

## 软约束例外

- React 函数组件、Hooks、纯工具函数、一次性脚本允许使用函数式风格。
- 当函数式实现明显更短、更清晰、可测试性更好时，可保留函数式方案。
- 若当前项目模块已有稳定范式（例如函数式状态管理），应优先保持一致性。

## 输出要求

- 提供代码实现时，默认先给出 OOP 组织版本（如类、对象协作、接口分层）。
- 若未采用 OOP 方案，需用 1 句话说明原因（如上下文约束、可读性或生态惯例）。
- 在 OOP 方案中避免过度工程化：类数量与抽象层级应与问题复杂度匹配。
